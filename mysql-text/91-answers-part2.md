## 第6章

### 理解度チェック

**問 6.1 の解答**

- ① **内部結合**（`INNER JOIN`）
- ② **左外部結合**（`LEFT JOIN`）
- ③ **`NULL`**

**解説**

3つとも 6.3.2 の表にまとまっています。

| 書き方 | 左の行に相手がいるとき | 左の行に相手がいないとき |
|-------|---------------------|----------------------|
| `INNER JOIN` | 相手の数だけ行が出る | **その行は消える** |
| `LEFT JOIN` | 相手の数だけ行が出る | **右側を `NULL` にして1行出る** |

③が `0` でも空文字でもなく **`NULL`** であることが重要です。
`NULL` は「値が入っていない」という印でした（第1章 1.3.1）。
この `NULL` の扱いが、6.3.3（`COALESCE`）・6.3.4（`WHERE` の罠）・
6.5.3（`COUNT` の引数）の3つの落とし穴すべての原因になっています。

**問 6.2 の解答**

**2**（結合条件が無いため、すべての組み合わせが作られた）

**解説**

これが**直積**（クロス結合）です（6.2.2）。
20 × 4 = 80 で、`products` の1行ごとに `categories` の4行が全部くっつきます。

**怖いのは、エラーが1つも出ないこと**です。
`category_id` が `1` のマグカップに「文房具」が付いた行が、平然と結果に混ざります。

1 は「複製」という言い方が誤りです。複製ではなく**組み合わせ**が作られています。
3 は `categories` に重複はありません（`SELECT * FROM categories;` で4行と確認できます）。
4 の「上限 80 行」という決まりは MySQL にありません。

この形を防ぐために、この本ではカンマ区切りを使わず
**`INNER JOIN ... ON`** と書きます。`ON` を忘れれば構文エラーで止まってくれます。

**問 6.3 の解答**

**2**（相手側の列の条件を `WHERE` に書いたため、相手がいない行が捨てられている）

**解説**

6.3.4 でそのまま扱った罠です。

`LEFT JOIN` は、受付の注文が無い顧客にも「右側が `NULL` の行」を作ります。
ところが `WHERE o.status = '受付'` は、**結合が終わったあとに**働きます。
`NULL = '受付'` は真にならないので（3.3.4）、その行は捨てられます。

結果として `INNER JOIN` と同じ4行だけが残りました。

直し方は、条件を `ON` に移すことです。

```sql
SELECT c.name AS 顧客名, o.id AS 注文番号
FROM customers AS c
LEFT JOIN orders AS o ON c.id = o.customer_id AND o.status = '受付'
ORDER BY c.id;
```

これで8行になります。

1 は逆です。`INNER JOIN` にすると、いまと同じ4行のままです。
3 は、`ON` の左右を入れ替えても結果は変わりません（6.2.2）。

> **覚え方**
> **`LEFT JOIN` の相手側の列を `WHERE` に書いたら、いったん手を止める。**
> 書いてよいのは `IS NULL` のときだけです（6.3.3）。

**問 6.4 の解答**

**2**（`1`）

**解説**

6.5.3 で実際に見た結果です。

`LEFT JOIN` は、相手がいない顧客にも**「右側が全部 `NULL` の行」を1行**作ります。
`COUNT(*)` は**行を数える**ので、その行も1行として数え、`1` を返します。

`0` にしたいなら、**相手側の主キー**を指定します。

```sql
COUNT(o.id)
```

`o.id` は `NULL` なので数えられず、`0` になります。

この違いが怖いのは、**「注文が1件ある人」と「0件の人」が、どちらも `1` と表示される**ことです。
エラーにならないので、そのまま資料になってしまいます。

**`LEFT JOIN` したら `COUNT(*)` を使わない**、と決めておいてください。

**問 6.5 の解答**

**解答例**

> `WHERE` は集計より前（②）に働くので `COUNT` はまだ計算されておらず、
> `HAVING` は集計のあと（⑤）に働くので計算済みの結果を条件にできるから。

**解説**

6.5.4 の実行順の図がそのまま答えになります。

```text
① FROM / JOIN → ② WHERE → ③ GROUP BY → ④ 集計関数
→ ⑤ HAVING → ⑥ SELECT → ⑦ ORDER BY → ⑧ LIMIT
```

`WHERE` に `COUNT(*)` を書くと、次のエラーで止まります。

```text
ERROR 1111 (HY000): Invalid use of group function
```

この図は、もう1つの疑問にも答えます。
**別名を付けるのは⑥の `SELECT` なので、②の `WHERE` では別名を使えず、
⑦の `ORDER BY` では使える**、という非対称もここから説明できます。

| 句 | 順番 | 集計関数 | 別名 |
|----|------|---------|------|
| `WHERE` | ② | 書けない | 使えない |
| `HAVING` | ⑤ | 書ける | 使える |
| `ORDER BY` | ⑦ | 書ける | 使える |

> **よくある間違い**
> 「`HAVING` は `WHERE` の高機能版」ではありません。
> **集計結果を条件にするときだけ `HAVING`**、それ以外は `WHERE` です。
> `HAVING` で行の絞り込みをすると、捨てる行をいったん全部まとめてから捨てることになり、
> 無駄な計算が増えます（6.5.4）。

**問 6.6 の解答**

**解答例**

> 足す対象の行が1つも無いとき。`0` は「合計したら0だった」、
> `NULL` は「合計する値がそもそも無かった」という意味なので別物である。

**解説**

6.5.3 で、渡辺さくらさんの購入金額が `NULL` になったのがこれです。

`LEFT JOIN` で相手がいなかった行では、`oi.quantity * oi.unit_price` が `NULL` になります。
`SUM` は `NULL` を飛ばして足すので、**飛ばした結果、足すものが残らず** `NULL` を返します。

金額として画面に出すなら `0` にします（6.3.3）。

```sql
COALESCE(SUM(oi.quantity * oi.unit_price), 0)
```

**「0円の顧客」と「値が無い顧客」を区別したい場面もあります。**
たとえば「全額返金されて合計0円になった人」と「一度も買っていない人」は、
業務上まったく違います。`COALESCE` で潰す前に、
**区別が要るかどうかを一度考えてください。**

**問 6.7 の解答**

**解答例**

> 個数は注文だけでも商品だけでも決まらず、
> 「この注文の、この商品」という**組み合わせ**に対して決まる値だから。

**解説**

6.7.1 で扱った、中間テーブルの役割の中心です。

`orders` に `quantity` を置くと、「注文4は何個？」という問いになります。
しかし注文4には3つの商品が入っており、2個・4個・2個とばらばらです。1つに決まりません。

`products` に置くと、「木のスープボウルは何個？」という問いになります。
注文4では2個ですが、別の注文では別の個数です。やはり決まりません。

**組み合わせに属する値は、組み合わせを表すテーブルに置く。**
これが中間テーブルが「ただの繋ぎ」ではない理由です。

`unit_price` も同じ理由でここにありますが、こちらには
**「その時点の記録」を残す**というもう1つの役割があります（2.5.1 / 5.5.3）。

### 演習 6.1 の解答

**解答例**

```sql
SELECT
    o.id         AS 注文番号,
    c.name       AS 顧客名,
    c.prefecture AS 都道府県,
    o.ordered_at AS 注文日時
FROM orders AS o
INNER JOIN customers AS c ON o.customer_id = c.id
WHERE o.status = '発送済'
ORDER BY o.ordered_at DESC;
```

実行結果:

```text
+--------------+---------------+--------------+---------------------+
| 注文番号     | 顧客名        | 都道府県     | 注文日時            |
+--------------+---------------+--------------+---------------------+
|           12 | 伊藤 慎二     | 福岡県       | 2026-09-01 18:22:00 |
|           10 | 高橋 美咲     | 北海道       | 2026-08-15 20:16:00 |
|            9 | 田中 陽子     | 東京都       | 2026-08-08 13:53:00 |
|            8 | 山本 大輔     | 大阪府       | 2026-08-01 11:09:00 |
|            7 | 佐藤 健       | 大阪府       | 2026-07-25 16:41:00 |
|            6 | 伊藤 慎二     | 福岡県       | 2026-07-19 08:58:00 |
|            4 | 高橋 美咲     | 北海道       | 2026-07-02 14:47:00 |
|            3 | 田中 陽子     | 東京都       | 2026-06-28 09:12:00 |
|            2 | 佐藤 健       | 大阪府       | 2026-06-11 19:05:00 |
|            1 | 田中 陽子     | 東京都       | 2026-06-03 10:24:00 |
+--------------+---------------+--------------+---------------------+
10 rows in set (0.00 sec)
```

**解説**

**出発点を `orders` にしたのがポイント**です。

作りたいのは「注文の一覧」なので、`FROM orders` から始めます。
顧客名と都道府県は、そこに**添える**情報です。

`INNER JOIN` で構わないのは、**注文には必ず顧客がいる**からです（6.3.2 の表）。
`orders.customer_id` は `NOT NULL` で、存在しない顧客を指す行もありません。
落ちる行が無いので、`LEFT JOIN` にする理由がありません。

**`WHERE o.status = '発送済'` を `ON` に書かないこと**

`INNER JOIN` では、`ON` に書いても `WHERE` に書いても同じ結果になります（6.3.4）。
それでも `WHERE` に書くのは、**役割が違うから**です（6.4.2 のルール）。

- `ON` は「どの行とどの行を同じ1行にするか」
- `WHERE` は「できあがった行のうち、どれを残すか」

この書き分けをしておくと、あとで `LEFT JOIN` に変えたときに壊れません。

> **よくある間違い**
> `ORDER BY o.ordered_at DESC` の `DESC` を忘れると、古い順（昇順）になります。
> 「新しい順」は**降順**です（3.4.2）。
>
> 1行目が注文番号 `1` になっていたら、`DESC` の書き忘れです。

> **別解：顧客側から書く**
>
> ```sql
> SELECT o.id AS 注文番号, c.name AS 顧客名, c.prefecture AS 都道府県, o.ordered_at AS 注文日時
> FROM customers AS c
> INNER JOIN orders AS o ON o.customer_id = c.id
> WHERE o.status = '発送済'
> ORDER BY o.ordered_at DESC;
> ```
>
> `INNER JOIN` なので、これでも**まったく同じ 10 行**が返ります。
> ただし、読む人は `FROM customers` を見て「顧客の一覧かな」と思います。
> **`FROM` に書くテーブルは、その問い合わせの主役**にしてください。

### 演習 6.2 の解答

**解答例**

```sql
SELECT
    c.name       AS 分類,
    COUNT(*)     AS 商品数,
    SUM(p.stock) AS 在庫合計,
    MAX(p.price) AS 最高価格
FROM categories AS c
INNER JOIN products AS p ON p.category_id = c.id
GROUP BY c.id, c.name
ORDER BY 在庫合計 DESC;
```

実行結果:

```text
+--------------+-----------+--------------+--------------+
| 分類         | 商品数    | 在庫合計     | 最高価格     |
+--------------+-----------+--------------+--------------+
| 文房具       |         5 |          322 |         4200 |
| 収納         |         5 |          112 |         3600 |
| キッチン     |         5 |          106 |         5800 |
| 食器         |         5 |           94 |         3200 |
+--------------+-----------+--------------+--------------+
4 rows in set (0.00 sec)
```

**解説**

**`GROUP BY c.id, c.name` と2つ書く理由**が、この問題の山です（6.5.2）。

- `c.id`：**まとめる単位**。同じ名前の分類があっても別物として扱うため（5.3.3）
- `c.name`：`SELECT` 句に出すため。書かないと `ERROR 1055` になる

`c.name` だけで `GROUP BY` しても、いまのデータでは同じ結果になります。
それでも主キーを書くのは、**「分類ごと」の「ごと」が何を指すかを SQL に明示する**ためです。

**`COUNT(*)` を使ってよい理由**

6.5.3 で「`LEFT JOIN` したら `COUNT(*)` を使わない」と書きました。
ここは `INNER JOIN` なので、**結果に出てくる行はすべて商品が実在する行**です。
`NULL` で埋められた行は1つもないので、`COUNT(*)` で正しく数えられます。

`COUNT(p.id)` と書いても同じ結果になります。**迷ったらそちらでも構いません。**

**`ORDER BY 在庫合計 DESC` に別名を使えるのはなぜか**

`ORDER BY` は⑦、別名を付ける `SELECT` は⑥なので、間に合っています（6.5.4）。

`ORDER BY SUM(p.stock) DESC` と書いても同じです。
**同じ式を2回書かずに済む**ぶん、別名のほうが読みやすくなります。

> **よくある間違い**
> `category_id` が結果に出ていたら、`categories` を結合していません。
>
> ```sql
> -- 分類の名前が出ない
> SELECT category_id, COUNT(*), SUM(stock), MAX(price) FROM products GROUP BY category_id;
> ```
>
> これも動きますが、**「1」「2」という番号のままでは読めません。**
> 番号を名前にするのが、この章で結合を学んだ理由です（6.1.2）。

### 演習 6.3 の解答

**解答例（1：`LEFT JOIN`）**

```sql
SELECT c.name AS 顧客名
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

**解答例（2：サブクエリ）**

```sql
SELECT name AS 顧客名
FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);
```

実行結果（どちらも同じ）:

```text
+------------------+
| 顧客名           |
+------------------+
| 渡辺 さくら      |
+------------------+
1 row in set (0.00 sec)
```

**危険になる条件（解答例）**

> `orders.customer_id` に `NULL` が入りうる場合、`NOT IN` の結果が常に0件になるので危険。

**解説**

**1：なぜ `IS NULL` に `o.id` を選ぶのか**

`LEFT JOIN` で相手が見つからなかったとき、右側の列は**全部 `NULL`** になります（6.3.1）。
どの列で判定してもよさそうに見えますが、そうではありません。

`o.status` で判定すると、**もともと `status` が `NULL` の注文行**があった場合に、
「注文はあるが `status` が空の顧客」まで引っかかってしまいます。

`orders.id` は主キーなので、**元のデータでは絶対に `NULL` になりません**（5.3.1）。
`NULL` であることが「相手がいなかった」ことだけを意味します（6.3.3）。

**2：なぜ `NOT IN` が危険なのか**

`NULL` は「値が分からない」という印です（3.3.4）。
「`id` は `NULL` と違うか？」という問いには、**分からないので真と答えられません。**

`NOT IN` は「かっこの中のどれとも違う」という条件なので、
候補に `NULL` が1つでも混ざると、**どの行も条件を満たさなくなります。**

```sql
SELECT name FROM customers WHERE id NOT IN (1, 2, NULL);
```

```text
Empty set (0.01 sec)
```

いまの `shop` で 2 の書き方が動いたのは、`orders.customer_id` が `NOT NULL` だからです。
`DESCRIBE orders;` で確認できます。

```sql
DESCRIBE orders;
```

実行結果:

```text
+-------------+-------------+------+-----+---------+----------------+
| Field       | Type        | Null | Key | Default | Extra          |
+-------------+-------------+------+-----+---------+----------------+
| id          | int         | NO   | PRI | NULL    | auto_increment |
| customer_id | int         | NO   |     | NULL    |                |
| ordered_at  | datetime    | NO   |     | NULL    |                |
| status      | varchar(10) | NO   |     | NULL    |                |
+-------------+-------------+------+-----+---------+----------------+
4 rows in set (0.00 sec)
```

`customer_id` の `Null` 列が **`NO`** になっていることを確かめてください（2.4.4）。

> **この本の方針**
> **「〜が無いもの」を探すときは、`LEFT JOIN` + `IS NULL` を使ってください。**
> 相手の列が `NULL` を許すかどうかを毎回調べなくて済み、
> あとで列の定義が変わっても壊れません。
>
> `NOT IN` は、**候補が固定の値のとき**（`WHERE status NOT IN ('キャンセル')` など）に使います。

> **別解：`NOT EXISTS` を使う**
>
> ```sql
> SELECT c.name AS 顧客名
> FROM customers AS c
> WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.id);
> ```
>
> これは相関サブクエリ（6.6.3）です。**`NULL` の問題は起きません。**
> 「その顧客の注文が1行も存在しない」という日本語に近い形で書けます。
> この本では扱いませんが、実務でよく見かける形なので、読めるようにしておいてください。

### 演習 6.4 の解答

**解答例**

```sql
SELECT
    c.name                           AS 顧客名,
    SUM(oi.quantity * oi.unit_price) AS 購入金額
FROM customers AS c
INNER JOIN orders      AS o  ON o.customer_id = c.id
INNER JOIN order_items AS oi ON oi.order_id = o.id
WHERE o.status <> 'キャンセル'
GROUP BY c.id, c.name
HAVING SUM(oi.quantity * oi.unit_price) >= 10000
ORDER BY 購入金額 DESC;
```

実行結果:

```text
+---------------+--------------+
| 顧客名        | 購入金額     |
+---------------+--------------+
| 佐藤 健       |        28060 |
| 高橋 美咲     |        18750 |
| 田中 陽子     |        18560 |
| 山本 大輔     |        13360 |
| 伊藤 慎二     |        10920 |
+---------------+--------------+
5 rows in set (0.00 sec)
```

**条件をどちらの句に書いたか（解答例）**

> 「キャンセルを除く」は注文1件ずつを見れば判断できるので `WHERE` に書いた。
> 「10,000 円以上」は合計してからでないと判断できないので `HAVING` に書いた。

**解説**

**2つの条件の性質がまったく違う**ことに気づけたかどうかが、この問題の狙いです。

実行される順番（6.5.4）に当てはめると、迷う余地がなくなります。

```text
① FROM / JOIN  … customers + orders + order_items を繋ぐ（37 行）
② WHERE        … キャンセルの注文の明細を捨てる ← ここで落とす
③ GROUP BY     … 顧客ごとにまとめる
④ 集計関数     … SUM を計算する
⑤ HAVING       … 合計が 10,000 未満のまとまりを捨てる ← ここで落とす
⑥ SELECT
⑦ ORDER BY     … 購入金額の降順
```

**②でキャンセルを落としておくのが大事**です。
落とさずに `HAVING` だけで絞ると、鈴木一郎さんのキャンセル注文（5,480 円）が
合計に入ってしまいます。

**`<>` は「等しくない」**でした（3.2.2）。`!=` と書いても同じです。

**`HAVING` に別名を使えるか**

MySQL では `HAVING 購入金額 >= 10000` と書いても動きます。
ただし**この書き方は MySQL 以外では動かないことがあります。**
`HAVING` は⑤、`SELECT` は⑥なので、本来は間に合っていないからです。

この本では、**`HAVING` には式をそのまま書きます。**

> **よくある間違い**
> `WHERE o.status <> 'キャンセル'` を `HAVING` に移すと、
> `ERROR 1054`（そんな列は無い）になります。
>
> ```text
> ERROR 1054 (42S22): Unknown column 'o.status' in 'having clause'
> ```
>
> `GROUP BY` でまとめたあとの世界には、**`GROUP BY` に書いた列と集計結果しかありません。**
> `o.status` はすでに消えています。
>
> このエラーは、「`HAVING` は `WHERE` の代わりではない」ことを
> データベース側から教えてくれているものです。

> **別解：`LEFT JOIN` で全員を出してから絞る**
>
> ```sql
> SELECT c.name AS 顧客名,
>        COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS 購入金額
> FROM customers AS c
> LEFT JOIN orders      AS o  ON o.customer_id = c.id AND o.status <> 'キャンセル'
> LEFT JOIN order_items AS oi ON oi.order_id = o.id
> GROUP BY c.id, c.name
> HAVING 購入金額 >= 10000
> ORDER BY 購入金額 DESC;
> ```
>
> **キャンセルの条件が `ON` に移っている**ことに注目してください（6.3.4）。
> `LEFT JOIN` では、`WHERE` に書くと注文の無い顧客が消えてしまいます。
>
> 結果は同じ5行です。10,000 円以上という条件があるので、
> 0円の渡辺さくらさんは `HAVING` で落ちます。
>
> **今回は `INNER JOIN` のほうが素直です。**
> 「10,000 円以上の顧客」を探すのに、0円の人を残す必要がないからです。

```sql
    p.name             AS 商品名,
    COUNT(pt.tag_id)   AS タグ数
FROM products AS p
LEFT JOIN product_tags AS pt ON pt.product_id = p.id
GROUP BY p.id, p.name
```

**タグが0個の商品でも数えられているか**を確かめます。

```sql
SELECT p.name AS 商品名, COUNT(pt.tag_id) AS タグ数

LEFT JOIN product_tags AS pt ON pt.product_id = p.id
WHERE p.id = 2
```

実行結果:

```text

+--------------------+-----------+
```

**`0` と出れば正解**です。`1` と出たら `COUNT(*)` を使っています。

**`LEFT JOIN` を使う理由（解答例）**

> `INNER JOIN` だとタグが付いていない商品が結果から落ちてしまい、
> 「タグが0個」という状態そのものを数えられなくなるから。

**解説**

2 も 3 も、**数えたい対象が「相手がいない側」にいる**問題です。

`INNER JOIN` で 3 を書くと、次のようになります。

```sql
-- タグが付いている 10 商品しか出てこない
SELECT p.name, COUNT(*)
FROM products AS p
INNER JOIN product_tags AS pt ON pt.product_id = p.id
GROUP BY p.id, p.name;
```

上位5件だけを見るぶんには同じ結果になります。
しかし「タグ数が少ない順」に並べ替えたとたん、**0個の商品が1つも出てきません。**
いちばん見たいものが見えない表になります。

**`COUNT(pt.tag_id)` と `COUNT(*)` の違い**は 6.5.3 のとおりです。
`LEFT JOIN` で作られた `NULL` の行を、`COUNT(*)` は1行として数えてしまいます。

タグ数が `2` の商品は4つあります。
2つ目のキー（`p.id`）が無いと、**同じ数のものの並びが決まりません**（3.4.3）。

**問 7.2 の解答**

**3**（索引は使われているが、100 万行のうち 83 万行を読むので速くならない）

**解説**

この章でいちばん間違えやすい点です（7.3.3 の「よくある間違い」）。

**問 7.3 の解答**

**3**（`WHERE ordered_at >= '2026-06-01'`）

**解説**

複合インデックスは、**かっこの中の左の列から順にしか使えません**（7.3.3）。

`(customer_id, ordered_at)` は、
「まず `customer_id` の順、同じ値なら `ordered_at` の順」に並んだ1本の索引です。
電話帳が「姓 → 名」の順に並んでいるのと同じで、
**姓を指定せずに名だけで探すことはできません。**

| 選択肢 | 左の列（`customer_id`）を使っているか | 効くか |
|-------|----------------------------------|-------|
| 1 | 使っている | **効く** |
| 2 | 使っている | **効く** |
| 3 | **使っていない** | **効かない** |
| 4 | 使っている | **効く** |

2 と 4 は、`AND` の左右が入れ替わっているだけで同じ条件です。
**`WHERE` に書く順番は関係ありません。** 関係するのは**索引の側の順番**です。

3 を効かせたいなら、`ordered_at` が左に来る索引をもう1本張ることになります
（本文では `idx_big_orders_ordered_customer` がそれにあたります）。

**問 7.4 の解答**

**解答例**

索引には `ordered_at` の値そのものが並んでいるので、
`DATE(ordered_at)` の結果は索引のどこにも無く、全行を関数に通して確かめるしかないから。

**解説**

7.5.1 の内容です。ポイントは「**索引に並んでいるのは、列の値そのもの**」という一点です。

| 書き方 | 索引の中に探す値があるか |
|-------|----------------------|
| `ordered_at >= '2026-06-06'` | **ある**（`2026-06-06 00:00:00` という値が並んでいる）→ 始点を引いて横に読める |
| `DATE(ordered_at) = '2026-06-06'` | **ない**（`2026-06-06` だけの値は索引に存在しない）→ 1行ずつ関数に通すしかない |

「関数を使うと遅くなる」と丸暗記すると、
`WHERE ordered_at >= DATE_SUB(CURDATE(), INTERVAL 7 DAY)` のような、
**問題のない書き方**まで避けてしまいます。
この書き方は**右辺**に関数があるだけで、右辺は先に1回計算されて1つの値になるので、索引は効きます。

**問題になるのは、列の側（左辺）に関数が掛かっているとき**です。
7.5.3 の型変換も、MySQL が**列の側を勝手に変換している**ので同じ形です。

**問 7.5 の解答**

**解答例**

`rows` は `EXPLAIN` が統計情報から出した**読むつもりの行数の見積もり**で、
`rows_examined` はスロークエリログに記録された**実際に読んだ行数**である。

**解説**

7.1.3 の注意と 7.4.3 の表の内容です。

| | いつ分かるか | 正確さ |
|-|------------|-------|
| `rows`（`EXPLAIN`） | **実行する前** | 見積もり。実際と数倍ずれることがある |
| `rows_examined`（スロークエリログ） | **実行したあと** | 実測。ずれない |

使い分けはこうです。

- **本番の重い SQL を調べたい** → 実行せずに済む `EXPLAIN`（7.4.1）
- **本当に直ったかを確かめたい** → 実測の `rows_examined`

7.3.3 では `rows` が 125282 と出たのに実際は 65536 でした。
**見積もりは、桁を見るためのもの**だと思ってください。

**問 7.6 の解答**

**解答例**（2つ書ければ正解）

- `INSERT` / `UPDATE` / `DELETE` のたびに索引の側も書き換えるので、**書き込みが遅くなる**
- 索引は元のテーブルとは別に持つので、**ディスクとメモリの容量を食う**

**解説**

7.6.1 と 7.6.2 で実際に測った2点です。

| 代償 | この章での実測 |
|------|--------------|
| 書き込み | 10 万行の `INSERT` が 0.84 秒 → **2.44 秒**（索引4本） |
| 容量 | 索引だけで **88 MB**（データ本体は 100 MB） |

次のように書けていても正解です。

- 「使われない索引は、ただ書き込みを遅くして容量を食うだけになる」（7.6.3 の①）
- 「索引がメモリに載り切らなくなると、ディスクを読みに行くので急に遅くなる」（7.6.2）

3つ目として**オプティマイザが迷う**という代償もあります。
索引が増えるほど、MySQL は「どれを使うか」の検討に時間をかけることになります。
ここでは書けていなくて構いません。

**表**

| | `type` | `key` | `rows` | 速いか遅いか |

| A | `const` | `PRIMARY` | 1 | 速い（0.00 秒） |
| B | `ref` | `idx_big_orders_code` | 1 | 速い（0.00 秒） |
| C | `index` | `idx_big_orders_code` | 約 97 万 | **遅い（0.37 秒）** |

**B と C が違う理由（解答例）**

索引は `code` の値を**先頭の文字から順に並べて**持っているので、
`ORD-0500000` と一致する行はひとかたまりの位置にあるが、
**末尾が `0500000` の行は索引の中に散らばっていて**、全部見るしかないから。

**解説**

**A の `const`**

`id` は主キーなので、テーブルを作った時点で索引が付いています（7.2.3）。
`type` の `const` は「主キー（や `UNIQUE`）で1行に確定する」という意味で、`type` の中では最速です。

**B の `ref`**

7.3.1 で張った `idx_big_orders_code` が使われています。
`Extra` に **`Using index`** と出ていたはずです。
これは「索引の中だけで答えが出せた」という印で、**速い印**です（7.4.2）。
`SELECT id, code` の 2 列は、どちらも `code` の索引の中にあります
（二次インデックスの葉には主キーの値が入っているため。7.2.3）。
だからテーブル本体を読みに行く必要がありませんでした。

**C の `index`**

**`key` に索引の名前が出ているのに遅い**、という 7.3.3 と同じ形です。
`possible_keys` が `NULL` になっていることにも注目してください。
これは「**絞り込みに使える索引が1本も無い**」という意味です。
索引は読んでいますが、**絞り込みには使えず、頭から最後まで全部読んでいます。**

**この3つの並びが、この章の要約になっています**

| | 索引で**絞り込めた**か | 結果 |
|-|--------------------|------|
| A | 絞り込めた（主キー） | 1 行だけ読む |
| B | 絞り込めた（`code` の索引） | 1 行だけ読む |
| C | **絞り込めなかった** | 97 万行読む |

判断材料は `type` でも `key` でもなく、**`rows`** です。

### 演習 7.2 の解答

**解答例**

```sql
SELECT COUNT(*) FROM big_orders
WHERE ordered_at >= '2026-03-01' AND ordered_at < '2026-04-01';
```

実行結果:

```text
+----------+
| COUNT(*) |
+----------+
|    99200 |
+----------+
1 row in set (0.04 sec)
```

**直す前と後**

| | 秒数 | `type` | `rows` |
|-|------|--------|--------|
| `YEAR(...) = 2026 AND MONTH(...) = 3` | 0.26 秒 | `index` | 約 97 万 |
| `>= '2026-03-01' AND < '2026-04-01'` | **0.04 秒** | **`range`** | 約 10 万 |

**解説**

7.5.1 の書き換えそのものです。`YEAR()` も `MONTH()` も、
**列の側に掛かった関数**なので、索引に並んでいる値とは別物になります。

**「3月ぶん」の範囲の書き方**

```sql
-- ✅ 正しい
WHERE ordered_at >= '2026-03-01' AND ordered_at < '2026-04-01'
```

終端は **4月1日未満**です。「3月31日以下」と書くと、
`ordered_at` が `DATETIME` なので `2026-03-31 00:00:00` として扱われ、
**3月31日の 00:00:01 以降がすべて漏れます**（7.5.1 の「よくある間違い」／3.3.3）。

```sql
-- ❌ 3月31日のほとんどが漏れる
WHERE ordered_at BETWEEN '2026-03-01' AND '2026-03-31'
```

件数が **99200** になっていれば、漏れていません。
`99200` ではなく `96000` あたりになっていたら、終端の書き方を見直してください。

> **`key` に出る索引名は、手元と違うことがあります**
> 執筆時の環境では、`(ordered_at, customer_id)` ではなく
> `(customer_id, ordered_at)` の索引が選ばれ、
> `Extra` に `Using index for skip scan` と出ました。
> MySQL が「`customer_id` は 8 種類しかないので、8 回に分けて範囲を読めばよい」と判断したためです。
> **どちらが選ばれても正解です。** 見るのは `type` と `rows` です。

### 演習 7.3 の解答

**1. `status` ごとの件数**

```sql
SELECT status, COUNT(*) AS 件数 FROM big_orders GROUP BY status;
```

実行結果:

```text
+-----------------+--------+

+-----------------+--------+
```

**3. キャンセル（全体の約 7%）**

```text
1 row in set (0.02 sec)

         type: ref
          key: idx_big_orders_status
         rows: 140006
        Extra: Using index
```

**4. 発送済（全体の約 67%）**

```text
         type: ref
          key: idx_big_orders_status
         rows: 488906
        Extra: Using index
```

**5. 理由（解答例）**

`status` は3種類しかなく、`発送済` は全体の約 67% を占めるので、
索引を引いてもほとんどの行が該当してしまい、全件走査とほぼ同じ量を読むことになるから。
`キャンセル` は約 7% しか該当しないので、索引で大半の行を捨てられる。

**解説**

**`type` は両方とも `ref` です。** つまり、
**「`type` が良い＝速い」ではない**ことが、ここでもう一度確かめられます。

違いが出るのは `rows` と秒数だけです。

| 値 | 全体に占める割合 | `rows`（見積もり） | 秒数 |
|----|--------------|------------------|------|
| `キャンセル` | 約 7%（65536 / 983040） | 140006 | **0.02 秒** |
| `発送済` | 約 67%（655360 / 983040） | 488906 | **0.23 秒** |

7.6.3 の表と照らし合わせてください。

| 割合 | 効き方 |
|------|-------|
| 1% 未満 | 非常によく効く |
| 数% 〜 2割 | 効く ← **キャンセル（7%）はここ** |
| 3割以上 | ほとんど効かない ← **発送済（67%）はここ** |

**ここから言えること**

「`status` にインデックスを張るべきか」という問いに、**1つの答えはありません。**

- 「キャンセルの一覧」を出す画面が主なら → **張る価値がある**
- 「発送済の一覧」が主なら → **張っても効かないので、書き込みが遅くなるだけ**（7.6.1）

**どの値で絞ることが多いか**まで見ないと決められない、ということです。
これが 7.6.3 の⑤「測ってから決める」の意味です。

> **`SELECT COUNT(*) FROM big_orders WHERE status = '受付';` はどうなるか**
> 受付は約 27%（262144 / 983040）で、ちょうど境目のあたりです。
> 執筆時の環境では **0.09 秒**（`type: ref` / `rows: 488906`）でした。
> キャンセル（0.02 秒）より遅く、発送済（0.23 秒）より速い、という中間の結果です。
> **割合が増えるほど、なめらかに遅くなっていく**ことが3つの値で確かめられます。
>
> なお、この索引を**張っていない**状態で `受付` を数えると `type: ALL` になります。
> MySQL は、索引があってもなくても「どちらが速いか」を見積もって決めています（7.6.3 の②）。

**6. 後始末**

```sql
DROP INDEX idx_big_orders_status ON big_orders;
```

外し忘れると、以降の演習で `EXPLAIN` の `possible_keys` に
`idx_big_orders_status` が混ざって読みにくくなります。

### 演習 7.4 の解答

**解答例**

```text
+---------------+--------+
2 rows in set (0.10 sec)
```

**`EXPLAIN` の結果**

```text

| id | table | type   | key                             | ref       | rows   | Extra                        |
+----+-------+--------+---------------------------------+-----------+--------+------------------------------+
```

（列を絞って載せています。手元では 12 列が表示されます。）

**3つの答え**

1. **2 行**（結合したテーブルの数だけ行が出る）
2. **`customers`（`c`）を先に読んでいる**（`EXPLAIN` は上から読む順に並ぶ）
3. **`idx_big_orders_customer_ordered`**（7.3.3 で張った `(customer_id, ordered_at)` の索引）

**解説**

**なぜ `customers` が先なのか**

`customers` は 8 行しかありません。
そのうち東京都は3人です（田中・鈴木・渡辺）。

**先に小さいほうを絞ってから、大きいほうを引く**のが速いので、
MySQL は `customers` を先に読むことを選びました。
`FROM` に `big_orders` を先に書いていても、この順番は変わりません
（**`EXPLAIN` の並びは、書いた順ではなく読む順です**。7.4.2）。

**`c` が `type: ALL` でよい理由**

8 行しかないテーブルは、索引を引く手間をかけるより全部読んだほうが速いからです（7.4.2 の囲み）。
**`ALL` が出ても、`rows` が 8 なら問題ありません。**

**`b` の `ref` と `ref` 列**

`b` の行の `ref` 列に **`shop.c.id`** と出ています。
これは「`customers` の `id` の値を使って `big_orders` を引く」という意味です。
つまり、東京都の顧客3人ぶん、**`customer_id` で3回引いている**ということです。

**`Using index` が出ている理由**

必要な列（`customer_id` と `ordered_at`）が、どちらも
`(customer_id, ordered_at)` の索引の中にあるからです（7.4.2 のカバリングインデックス）。
テーブル本体を読みに行かずに済んでいます。

**結果が 2 行になる理由**

東京都の顧客は3人ですが、**渡辺 さくらさんは注文が1件もありません**（第6章 演習 6.3 の答え）。
`INNER JOIN` なので、相手がいない行は消えます（6.3.2）。
「注文0件の人も 0 と出したい」なら `LEFT JOIN` にして
`COUNT(b.id)` を使うことになります（6.5.3）。

**やってはいけない書き方**

```sql
-- ❌ 索引が効かなくなります
WHERE YEAR(b.ordered_at) = 2026 AND MONTH(b.ordered_at) = 6
```

7.5.1 と演習 7.2 と同じ形です。**結合していても話は同じ**です。

### 演習 7.5 の解答

**記録を始める**

```sql
SET GLOBAL log_output = 'TABLE';
SET GLOBAL long_query_time = 0.1;
SET GLOBAL slow_query_log = ON;
```

**3本を実行したあと、記録を見る**

```sql
SELECT start_time, query_time, rows_examined,
       CONVERT(sql_text USING utf8mb4) AS sql_text
FROM mysql.slow_log
ORDER BY query_time DESC
LIMIT 3\G
```

実行結果:

```text
*************************** 1. row ***************************
   start_time: 2026-09-16 07:37:18.220071
   query_time: 00:00:00.196833
rows_examined: 983040
     sql_text: SELECT COUNT(*) FROM big_orders WHERE SUBSTRING(code, 1, 8) = 'ORD-0500'
1 row in set (0.00 sec)
```

**書き直した SQL**

```sql
SELECT COUNT(*) FROM big_orders WHERE code LIKE 'ORD-0500%';
```

実行結果:

```text
+----------+
| COUNT(*) |
+----------+
|     1000 |
+----------+
1 row in set (0.00 sec)
```

`EXPLAIN`:

```text
         type: range
          key: idx_big_orders_code
         rows: 1000
        Extra: Using where; Using index
```

**記録を止める**

```sql
SET GLOBAL slow_query_log = OFF;
```

**解説**

**なぜ1本だけが記録されたのか**

| SQL | 秒数 | 記録されたか |
|-----|------|------------|
| `SUBSTRING(code, 1, 8) = 'ORD-0500'` | 0.20 秒 | **された**（0.1 秒超え） |
| `ordered_at >= ... AND < ...` | 0.00 秒 | されない |
| `code = 'ORD-0777777'` | 0.00 秒 | されない |

**遅いものだけが勝手に残る**。これがスロークエリログの価値です（7.4.3）。
20 本の `SELECT` がある画面でも、犯人が1本に絞られます。

**`SUBSTRING(code, 1, 8)` がだめな理由**

7.5.1 と同じです。**列の側に関数が掛かっています。**
索引に並んでいるのは `code` の値そのもの（`ORD-0500000`）であって、
`SUBSTRING(code, 1, 8)` の結果（`ORD-0500`）ではありません。

**`LIKE 'ORD-0500%'` が効く理由**

`%` が**末尾にしかない**（前方一致）ので、
`ORD-0500` で始まる行は索引の中でひとかたまりになっています（7.5.2）。
始点を引いて、そこから横に 1000 行読むだけで済みます。

**間違えやすい書き方**

```sql
-- ❌ これは索引が効きません
WHERE code LIKE '%ORD-0500%'
```

前後に `%` を付けると後方一致を含むので、索引が使えません（7.5.2）。
**必要な `%` だけを書いてください。**

```sql
-- ❌ これは 0 件になります
WHERE code = 'ORD-0500%'
```

`=` に `%` を書いても、ワイルドカードとしては働きません（3.3.1）。
`ORD-0500%` という文字列そのものを探してしまいます。

**`rows_examined` が 983040 であることの意味**

`EXPLAIN` の `rows` は見積もりでしたが、`rows_examined` は**実測**です（問 7.5）。
983,040 は `big_orders` の全行数なので、
**間違いなく全件走査だった**と確定できます。

**書き直したあと、もう一度測る**

7.4.3 の輪の⑤です。書き直した SQL をもう一度実行して、
`mysql.slow_log` に**新しい行が増えていない**ことを確かめてください。
増えていなければ、0.1 秒を切ったということです。

> **記録が1件も見つからないとき**
>
> ```sql
> SHOW VARIABLES LIKE 'long_query_time';
> SHOW VARIABLES LIKE 'slow_query_log';
> SHOW VARIABLES LIKE 'log_output';
> ```
>
> `0.100000` / `ON` / `TABLE` の3つがそろっているかを確かめてください
> （`SHOW VARIABLES` は 2.6.2 で使いました）。
> `docker compose down` して `up` し直すと**既定値に戻ります**（7.4.3 の注意）。
>
> 記録がたまりすぎて読みにくくなったら、次の1行で空にできます。
>
> ```sql
> TRUNCATE TABLE mysql.slow_log;
> ```

**問 8.5 の解答**

**危険なのは A。** 理由は、**f 文字列で SQL の文そのものを組み立てており、
`q` に `'` が含まれていると文字列の終わりをこちらで決められてしまうから。**

**解説**

8.4.2 の最後の囲み記事で扱った区別です。**両方とも f 文字列を使っています。**
違うのは「**何を作っているか**」です。

| | 作っているもの | 危険か |
|---|-------------|-------|
| A | **SQL の文**（`SELECT ... WHERE ...`） | **危険** |
| B | `LIKE` に渡す**値**（`%...%` というパターン） | 安全 |

B で `q` が最終的にどう扱われるかは、8.4.2 のログで確認しました。

```text
WHERE tasks.title LIKE %(title_1)s
[generated in 0.00013s] {'title_1': "%' OR '1'='1%"}
```

**SQL の本体に値が入っていません。** 値は別に渡されています。

**判定の手順**

迷ったら、次の順に見てください。

1. その文字列は、最終的に `text(...)` か `execute(...)` に渡されるか
2. 渡されるなら、その文字列に `{}` / `+` / `%` / `.format()` で外の値が入っているか
3. 入っているなら**危険**

**よくある間違い**

「`text()` を使っているから危険」と覚えると、8.4.3 の安全な形まで避けてしまいます。
**`text()` 自体は危険ではありません。** 危険なのは**組み立て方**です。

```python
# 安全（プレースホルダ）
text("SELECT id, title FROM tasks WHERE title LIKE :pattern")
```

| `ForeignKey("tasks.id", ondelete="CASCADE")` | `CONSTRAINT ... FOREIGN KEY ... ON DELETE CASCADE` | 5.4.2 / 5.4.4 |
| `server_default=func.now()` | `DEFAULT CURRENT_TIMESTAMP` | 5.2.2 |
| `Mapped[bool]` | **`tinyint(1)`** | 5.1.4 |

**`KEY task_id (task_id)` を自分で作っていない**ところが、いちばん気づきにくい点です。
MySQL は**外部キーの列にインデックスを自動で作ります**（8.2.1）。
制約を守るために「その `id` が `tasks` にあるか」を毎回引く必要があり、
索引が無いと `tasks` の全件走査になってしまうためです（7.1.2）。

**`created_at` に値を入れなかったのに時刻が入る**のは、
第4章 4.1.3 で扱った「列を省略したときの挙動」です。
省略された列には `DEFAULT` の値が入ります。
ここでの `DEFAULT` は `CURRENT_TIMESTAMP`（いまの時刻）でした。

**よくある間違い**

後片付けを `DELETE FROM comments;` と打ってしまう間違いです。
**`WHERE` が無いので全件消えます**（4.2.3 の `UPDATE` と同じ事故です）。
消してしまった場合は、8.2.2 の表のとおりに入れ直してください。

**打った手順**

`selectinload` を外した状態に戻します。


**解説**

`GET /tasks/1` が2本で止まる理由は、8.2.2 の最後のシーケンス図にあります。

1. `db.get(Task, 1)` で `tasks` を1行引く（1本目）
2. `TaskRead` が `task.comments` を読んだ瞬間に `comments` を引く（2本目）

**「タスク1件につきコメントの SELECT が1本」という構造は同じ**です。
違うのは、**タスクが1件しかない**ことです。

```text
一覧   ： 1 + タスクの件数     ← 件数が増えると増える（N+1）
1件取得： 1 + 1                ← いつも2本
```

**`selectinload` を付けても本数が変わらない**のは、
まとめる相手が1件しかないので「まとめる意味がない」からです。
`IN (1)` になるだけで、本数は同じ2本です。

**よくある間違い**

**`TRUNCATE` を忘れて、前の回の記録が足されている**間違いです。
4本のはずが8本、12本と増えていきます。

もう1つは、**ブラウザで `/docs` から実行している**場合です。
`/docs` を開くだけでは SQL は飛びませんが、
**「Try it out」を2回押していると2回ぶん記録されます。**
`curl` で1回だけ叩くほうが、数え間違いが起きません。

**補足：なぜ `LIKE 'SELECT%FROM%'` で絞るのか**

`general_log` には、`mysql` コマンド自身が打つ SQL も入ります。

```text
select @@version_comment limit 1
```

これには `FROM` が無いので、`LIKE 'SELECT%FROM%'` で落ちます（3.3.1）。
`ROLLBACK` や `Connect` の行も、`command_type` と `LIKE` の条件で落ちています。

```python
SEARCHABLE = {"title": "title", "owner_name": "owner_name"}


@router.get("/search2", response_model=list[dict])
```

**解説**

この演習の要点は、**`q` と `field` を別の扱いにする**ことです。

| 受け取るもの | 何になるか | 扱い方 |
|------------|----------|-------|
| `q` | SQL の**値** | **プレースホルダ**（`:pattern`） |
| `field` | SQL の**形**（列名） | **許可リスト**（`SEARCHABLE`） |

**f 文字列を使っていますが、埋め込んでいるのは `SEARCHABLE` の値だけ**です。
`field` に何が来ても、`SEARCHABLE.get(field)` を通った後の値しか SQL に入りません。
**外から来た文字が、そのまま SQL に入ることはありません**（8.4.3）。

**なぜ辞書にするのか**

```python
SEARCHABLE = {"title": "title", "owner_name": "owner_name"}
```

キーと値が同じなので、リストでもよさそうに見えます。

```python
# これでも動きます
SEARCHABLE = ["title", "owner_name"]
if field not in SEARCHABLE:
    raise HTTPException(...)
```

辞書にしておくと、**外から見える名前と、実際の列名を変えられます。**

```python
SEARCHABLE = {"title": "title", "owner": "owner_name"}
```

こうすれば `?field=owner` で探せます。
**列名をそのまま外に見せない**ことは、地味ですが役に立ちます。

**別解：ORM で書く**

`text(...)` を使わない書き方もできます。

```python
SEARCHABLE_COLUMNS = {"title": Task.title, "owner_name": Task.owner_name}


@router.get("/search3", response_model=list[dict])
def search_tasks3(
    q: str = Query(min_length=1),
    field: str = Query(default="title"),
    db: Session = Depends(get_db),
):
    column = SEARCHABLE_COLUMNS.get(field)
    if column is None:
        raise HTTPException(status_code=422, detail=f"{field} では検索できません")

    tasks = db.scalars(select(Task).where(column.like(f"%{q}%"))).all()
    return [{"id": task.id, "title": task.title} for task in tasks]
```

**辞書の値が、文字列ではなくモデルの列そのもの**になっています。
SQL の文字列を1文字も書かないので、こちらのほうが安全側に倒れています。
**実務では、まずこの形を検討してください。**

**よくある間違い**

**`field` をプレースホルダで渡そうとする**間違いです。

```python
# 動きません
sql = text("SELECT id, title FROM tasks WHERE :column LIKE :pattern")
```

エラーにはならず、**常に0件**になります。
`WHERE 'title' LIKE '%牛乳%'` という、
「`title` という**文字列**が `%牛乳%` に当てはまるか」という条件になるためです（8.4.3）。

もう1つは、**`search-ng` を消し忘れる**ことです。
安全な窓口を足しても、**危ない窓口が残っていれば意味がありません。**

### 演習 8.5 の解答

**解答のコード**

`fastapi-lesson/check_pool_limit.py`（ファイル全体）

```python
"""プールが足りなくなるところを見る（mysql-text 演習 8.5）。"""

import time

from sqlalchemy import create_engine

from app.config import settings

MAX_OVERFLOW = 0  # ここを 1 に変えて、もう一度実行する

engine = create_engine(
    settings.database_url,
    pool_size=2,
    max_overflow=MAX_OVERFLOW,
    pool_timeout=3,
)

borrowed = []
try:
    for i in range(1, 4):
        start = time.perf_counter()
        try:
            borrowed.append(engine.connect())
            print(f"{i} 本目: 借りられた（{time.perf_counter() - start:.1f} 秒）")
            print("   ", engine.pool.status())
        except Exception as error:
            print(f"{i} 本目: 失敗（{time.perf_counter() - start:.1f} 秒）")
            print("   ", type(error).__name__)
            print("   ", str(error).splitlines()[0])
finally:
    # 借りた接続は必ず返す
    for conn in borrowed:
        conn.close()
    print("返しました:", engine.pool.status())
```

```text

    Pool size: 2  Connections in pool: 0 Current Overflow: -1 Current Checked out connections: 1
2 本目: 借りられた（0.0 秒）
    Pool size: 2  Connections in pool: 0 Current Overflow: 0 Current Checked out connections: 2
3 本目: 失敗（3.0 秒）
    TimeoutError
    QueuePool limit of size 2 overflow 0 reached, connection timed out, timeout 3.00 (Background on this error at: https://sqlalche.me/e/20/3o7r)
返しました: Pool size: 2  Connections in pool: 2 Current Overflow: 0 Current Checked out connections: 0
```

**`max_overflow = 1` に変えたときの実行結果**

```text
1 本目: 借りられた（0.0 秒）
    Pool size: 2  Connections in pool: 0 Current Overflow: -1 Current Checked out connections: 1
2 本目: 借りられた（0.0 秒）
    Pool size: 2  Connections in pool: 0 Current Overflow: 0 Current Checked out connections: 2

    Pool size: 2  Connections in pool: 0 Current Overflow: 1 Current Checked out connections: 3

```

**`返しました` の行**では、どちらも `Checked out connections: 0` に戻っています。
`Connections in pool: 2` は、**切断せずに待機所に戻した2本**です（8.5.2）。

**MySQL 側の確認**（`max_overflow = 0` で2本借りている最中に打つ）

```sql
SHOW STATUS LIKE 'Threads_connected';
```

```text
+-------------------+-------+
| Variable_name     | Value |
+-------------------+-------+
| Threads_connected | 3     |
+-------------------+-------+
```

Python 側の2本と、**いま `mysql` で打っているぶんの1本**です（8.5.1 と同じ数え方）。

**違いの説明**

**同時に借りられる本数の上限は、`pool_size` と `max_overflow` の合計**である。
`max_overflow=0` なら 2 本、`max_overflow=1` なら 3 本まで借りられる。

**解説**

`pool_size` は「**待機所に置いておく本数**」、
`max_overflow` は「**足りないときに一時的に増やせる本数**」でした（8.5.2 の表）。

```text
同時に借りられる上限 = pool_size + max_overflow
既定では             = 5 + 10 = 15 本
```

**3本目が「エラーではなく、まず待つ」ところ**が重要です。
`pool_timeout=3` の3秒ぶん待ってから、あきらめて `TimeoutError` になりました。

**実際のアプリでは、この「待ち」が表に出ます。**
同時アクセスが増えると、**SQL は速いのに、レスポンスだけが遅くなります。**
待っているのは SQL の実行ではなく、**接続の順番待ち**です。

| 症状 | 疑うところ |
|------|----------|
| 特定の画面だけ遅い | 1本の SQL（第7章 `EXPLAIN`） |
| 一覧の画面だけ遅い | **本数**（8.3 の N+1） |
| **混んでいるときだけ全部遅い** | **プールの本数**（この演習） |

**`Current Overflow` の読み方**

慣れないと分かりにくい表示です。

| 表示 | 意味 |
|------|------|
| `Current Overflow: -1` | 待機所の枠が **1つ余っている** |
| `Current Overflow: 0` | 待機所の枠は**ちょうど使い切った** |
| `Current Overflow: 1` | 枠を超えて **1本、一時的に作った** |

**`max_overflow` を超えられない**のが、この演習で見た上限です。

**よくある間違い**

**借りた接続を返さずにスクリプトを終える**間違いです。
Python が終了すれば接続も切れるので実害は出ませんが、
**`finally` で必ず返す形を身に付けてください。**

アプリの中で返し忘れると、**プールが枯れたまま戻りません。**
fastapi-text 6.5.1 の `get_db` が `try` / `finally` で `close()` していたのは、これを防ぐためです。

もう1つは、**`pool_timeout` を指定せずに試して、30秒待たされる**ことです。
既定は 30 秒です（8.5.2 の表）。**待っているだけなので、止めずに待ってください。**
