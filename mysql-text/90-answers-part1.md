### 理解度チェック

**問 1.1 の解答**

- ① **遅く**
- ② **消える**（あとから書き戻した人に上書きされる）
- ③ **整合性**

**解説**

3つとも 1.1 で見た問題です。

①は、1件ほしいだけでもファイルを全部読んで先頭から比べる（**全件走査**）ためです（1.1.1）。
件数が 10 倍になれば、探す手間もおよそ 10 倍になります。

②で重要なのは、**エラーが1つも出ない**ことです（1.1.2）。
2人とも「保存できた」と思っています。気づくのは、ずっとあとになってからです。

③の**整合性**は「データどうしが食い違っていない状態」のことでした（1.1.3）。
型の崩れ・表記ゆれ・項目の欠け・`id` の重複は、どれも**書いた瞬間には何も起きません。**

**問 1.3 の解答**

**3** の「本人が自由に変更できるメールアドレス」

**解説**

主キーの3条件は「重複しない」「空にできない」「変わらない」でした（1.4.1）。
メールアドレスは1つ目と2つ目は満たせますが、**3つ目に反します。**

変わる値を主キーにしてはいけない理由は、**主キーが「指される側」だから**です（1.4.2）。
1.2.2 の `tasks.owner_id` を思い出してください。
もし主キーがメールアドレスだったら、`tasks` 側にもメールアドレスが入っています。
1人がアドレスを変えるたびに、**その人を指している全テーブルの全行**を直すことになります。

選択肢 4 の「生徒 `id` と授業 `id`」は、**複合主キー**として正しい形です（1.4.2 の補足）。
「主キーは1列でなければいけない」という決まりはありません。

**問 1.4 の解答**

次のうち、どれか1つが書けていれば正解です（1.2.2）。

- **表記ゆれが起きなくなる。** 担当者名は `owners` に1箇所しかなく、`tasks` には `id` しか入らないため
- **改姓しても `owners` の1行を直すだけで済む。** `tasks` 側は1行も変えなくてよい
- **存在しない担当者を指す行を拒否できる**（外部キー。第5章 5.4）
- **担当者の情報を増やすのが `owners` に列を足すだけで済む。** `tasks` は変えなくてよい

**解説**

どの答えも、根っこは同じ1点です。

> **同じ値を2箇所に持つのをやめた。**

1.1.3 の崩れは、ほとんどが「同じことを何度も書いた」ことから生まれていました。
**書く場所を1つにすれば、ずれようがありません。**

なお、**分けたら万事解決というわけではありません。**
担当者名つきの一覧を出すには、2つのテーブルを繋ぐ**結合**が必要になります（第6章）。
「どこまで分けるか」の判断基準は第5章 5.5 で扱います。

**問 1.5 の解答**

**取り出すための手順を書かず、「どういう条件のものがほしいか」だけを書くから。**
実際にどう取り出すかは DBMS が決める。

**解説**

1.2.3 で比べた2つを、もう一度並べます。

```python
result = []
for task in tasks:
    if not task["done"]:
        result.append(task["title"])
result.sort()
```

```sql
SELECT title FROM tasks WHERE done = 0 ORDER BY title;
```

Python のほうは、**行の順番を入れ替えると結果が変わります。**
「1件ずつ見る」「条件に合えば足す」「最後に並べ替える」という手順そのものだからです。

SQL のほうには、手順が1つも書かれていません。
「未完了の」「タイトルを」「順に並べて」という**条件だけ**です。

これは手抜きではなく、利点です。
データが 10 万件に増えたとき、**SQL を1文字も変えずに、
DBMS 側が効率のよい取り出し方に切り替えられます。**
DBMS が選んだ取り出し方を確認する方法は、第7章 7.4（実行計画）で扱います。

**問 1.6 の解答**

**`NULL` は「値がそもそも入っていない」状態、空文字（`''`）は「空という値が入っている」状態。**

**解説**

住所欄で考えると分かりやすくなります（1.3.1）。

| 状態 | 意味 |
|------|------|
| `NULL` | **まだ聞いていない。** 住所があるのかどうかも分からない |
| `''`（空文字） | **聞いたうえで、空だった。** 長さ 0 の文字列が入っている |

この違いは、第3章 3.3.4 で検索条件を書くときに効いてきます。
`NULL` は「等しいか」で比べられないため、専用の書き方（`IS NULL`）を使います。

> **補足**
> Python の `None`、JavaScript の `null` に近いものですが、
> **比べ方が違う**点だけ、いまのうちに引っかかりとして覚えておいてください。

**問 1.7 の解答**

**MySQL はサーバー型で、専用のプログラムを起動してそこへ接続する。
SQLite はファイル型で、専用のプログラムを起動せず1つのファイルを直接読み書きする。**

**解説**

fastapi-text 第6章で「データベースサーバーを起動する」作業をしなかったのは、
SQLite がファイル型だったからです（1.5.1）。
保存先は `app.db` という**1つのファイル**だけでした。

この本で MySQL を使うには、第2章で**先に MySQL を起動しておく**必要があります。
第0章 0.1.1 で Docker が使えるかを確認したのは、この起動のためです。

形が違うと、得意なことも変わります。

| | MySQL（サーバー型） | SQLite（ファイル型） |
|---|-----------------|------------------|
| 大勢が同時に書く | 得意 | 苦手（書き込みは1つずつ） |
| 準備 | 起動が必要 | 不要 |
| 向いている場面 | Web アプリの本番 | 手元の試作、アプリへの同梱 |

**書く SQL は、ほとんど同じです。** 違うのは準備と運用の部分です。

### 演習問題

### 演習 1.1 の解答

**テーブルの設計（解答例）**

**items**

| 列名 | 入れるデータの種類 | 補足 |
|------|-----------------|------|
| `id` | 整数 | **主キー** |
| `name` | 文字列 | 商品名 |
| `price` | 整数 | 円単位。1.3.1 の `INT` にあたる |
| `stock` | 整数 | 在庫数 |
| `category` | 文字列 | 分類 |

**主キー：`id`**

理由：**行を1つに特定するために用意された、意味を持たない連番だから**（1.4.2 の代理キー）。
`name` は同じ商品名が入る可能性があり、`category` は明らかに重複します。

**JSON に入っていた4つの崩れ**

| 崩れ | どこ | テーブルではなぜ起きないか |
|------|------|------------------------|
| 型がそろっていない | `"price": "800"` が文字列 | `price` 列を整数型にすると、**文字列は入らない**（1.3.1） |
| 表記がゆれている | `"category": "食器 "` に余分な空白 | **これはテーブルにしても防げません**（下記） |
| 項目が欠けている | `id: 3` の1行目に `stock` が無い | テーブルは**すべての行が同じ列を持つ**ので、列が消えることはない（1.2.1） |
| `id` が重複している | `id: 3` が2行ある | `id` を**主キー**にすると、同じ値は2行目で拒否される（1.4.1） |

**`stock` が `null` の行と `0` の行の違い**

- `0`：**在庫数を数えた結果、0 個だった**
- `null`（`NULL`）：**在庫数がまだ分からない。** 数えていない、あるいは記録していない

「在庫切れの商品を一覧する」ときに、この2つを同じに扱うと結果が変わります（1.3.1、第3章 3.3.4）。

**テーブルの形にしても、まだ防げないもの**

**`"食器"` と `"食器 "` の表記ゆれです。**

どちらも文字列としては正しい値なので、型の検査でも「空にしない」制約でも止まりません（1.1.3）。
このままだと、「食器の商品を数える」ときに2つに割れて出てきます。

根本的に直すには、**分類を別のテーブルに分けて、`items` は分類の `id` を持つ**形にします（1.2.2）。
そうすれば、「食器」という文字列は `categories` テーブルに1箇所しか存在しなくなります。

**解説**

この演習の狙いは、**「テーブルにすれば全部きれいになる」わけではない**と気づくことです。

テーブルの形が自動で防いでくれるのは、次の3つです。

1. **型の崩れ**（列の型で止まる）
2. **項目の欠け**（列が固定されているので起きない）
3. **主キーの重複**（主キーの制約で止まる）

一方で、**「同じ意味の値が、違う文字列で入る」問題は残ります。**
これを止めるのが 1.2.2 の「表を分ける」という考え方で、演習 1.2 でそれを実際にやります。

> **別解**
> `price` を整数ではなく小数の型にした人もいるかもしれません。
> 金額に小数の型を使うと、計算がわずかにずれることがあります。
> **金額を浮動小数点数で持たない**理由は、第5章 5.1.5 で扱います。
> この演習では、円単位の整数にしておけば十分です。

### 演習 1.2 の解答

**分けたあとのテーブル（解答例）**

**authors**（著者）

| id | name | birth_year |
|----|------|-----------|
| 1 | 夏目漱石 | 1867 |
| 2 | 芥川龍之介 | 1892 |

**books**（書籍）

| id | title | author_id |
|----|-------|-----------|
| 1 | 吾輩は猫である | 1 |
| 2 | こころ | 1 |
| 3 | 坊っちゃん | 1 |
| 4 | 羅生門 | 2 |

**members**（利用者）

| id | name |
|----|------|
| 1 | 田中 |
| 2 | 佐藤 |

**loans**（貸出）

| id | book_id | member_id | loaned_on |
|----|---------|-----------|-----------|
| 1 | 1 | 1 | 2026-09-01 |
| 2 | 2 | 2 | 2026-09-02 |
| 3 | 3 | 1 | 2026-09-03 |
| 4 | 4 | 1 | 2026-09-05 |

**主キー**：4つとも `id` 列（代理キー。1.4.2）

**相手の主キーを持つ列**（1.2.2 の手順4にあたるもの）

| どのテーブルの、どの列 | 何を指しているか |
|--------------------|----------------|
| `books.author_id` | `authors.id` |
| `loans.book_id` | `books.id` |
| `loans.member_id` | `members.id` |

3つあります。**1つのテーブルが2つ持つことも問題ありません**（`loans`）。

**もとの表にあった崩れと、解決したこと**

崩れ：**3行目の著者名が「夏目 漱石」になっている**（ほかの行は「夏目漱石」）。

分けたあと、著者名は `authors` テーブルに**1行しか存在しません。**
`books` が持っているのは `author_id` という数値だけなので、
**そもそも著者名を書き間違える場所がなくなりました。**

**増える手間**

「誰が、いつ、何という本を、誰の著書で借りたか」を1枚の表として見たいときは、
`loans` / `books` / `authors` / `members` の**4つを繋ぐ**必要があります。
この操作が**結合（JOIN）**で、**第6章**で扱います（3つ以上の結合は 6.4）。

**解説**

1.2.2 の4つの手順を、繰り返し出てくる列の数だけ回すのがこの演習です。

| 回 | 1. 繰り返している列 | 2〜3. 作る表 | 4. もとの表が持つ列 |
|----|------------------|------------|------------------|
| 1周目 | `book_author` / `author_birth_year` | `authors` | `books.author_id` |
| 2周目 | `member_name` | `members` | `loans.member_id` |
| 3周目 | `book_title` | `books` | `loans.book_id` |

**`author_birth_year` を `authors` に置く理由**が、この演習のいちばんの山です。

生年は**著者に属する情報**であって、本にも貸出にも属していません。
`books` に置くと、夏目漱石の本が3冊あるだけで `1867` が3回書かれます。
**生年が間違っていたときに3箇所直す**ことになり、1.1.3 の状態に逆戻りです。

判断の基準は 1.2.2 の手順2、
**「その値と、それにくっついてくる情報をまとめて別の表にする」**です。
「この値は、何が決まれば決まるのか」を考えてください。
生年は**著者が決まれば決まります。** だから `authors` に置きます。

> **別解**
> `books` を作らず、`loans` に `book_title` と `author_id` を直接持たせた人もいるかもしれません。
> 同じ本が2回貸し出されたときに書名が2回書かれるので、表記ゆれの余地が残ります。
> ただし、**「この図書館は同じ本を2回貸さない」という前提があるなら、それでも成り立ちます。**
> テーブルの分け方は、**扱う対象のルールによって変わります。**
> どこまで分けるかの判断基準は、第5章 5.5 で扱います。

> **よくある間違い**
> `loans` に主キーを付け忘れる人が多い箇所です。
> 「同じ人が同じ本を、別の日にもう一度借りる」ことがあるので、
> `book_id` と `member_id` の組だけでは1行に決まりません（1.4.1）。
> 連番の `id` を用意するか、`loaned_on` まで含めた組にする必要があります。

### 演習 1.3 の解答

**主キーの候補の評価（解答例）**

| 候補 | 重複しないか | 空にならないか | 変わらないか | 判定 |
|------|------------|--------------|------------|------|
| 会議室の名前 | ✕ 同じ部屋を何度も予約する | ○ | △ 部屋名を変えることはある | **✕** |
| 予約した人の社員番号 | ✕ 1人が何件も予約する | ○ | ○ | **✕** |
| 予約した日付 | ✕ 同じ日に何件も予約が入る | ○ | ✕ 予約日を変更することがある | **✕** |
| 予約の目的 | ✕ 「定例会議」が何度も入る | ✕ 空欄のことがある | ✕ あとから書き換えられる | **✕** |
| 連番の `id` | ○ | ○ | ○ | **○** |

**選んだ主キー：連番の `id`**

理由：**3つの条件をすべて満たし、現実の都合で値が変わることがないから**（1.4.2 の代理キー）。

**「予約の目的」を主キーにしてはいけない理由**

3条件の**すべてに反します。** とくに決定的なのは2つ目で、
**空欄のことがある**ためです。主キーは空（`NULL`）にできません（1.4.1）。

**「会議室の名前」だけでは主キーにできない理由**

**同じ会議室が何度も予約されるので、値が重複します**（1.4.1 の1つ目の条件）。
「第1会議室」という値の行が、何十行も並ぶことになります。

**複数の列を組み合わせれば決まる組み合わせ**

**「会議室の名前 ＋ 予約した日付 ＋ 開始時刻」**の3列の組み合わせです。
同じ部屋の、同じ日の、同じ時刻に2件の予約は入らないので、これで1行に決まります。

この形を**複合主キー**と呼びます（1.4.2 の補足）。

**解説**

この演習で確かめてほしいのは、
**「1列ずつ順に見ていけば、候補は機械的に落とせる」**ということです。
1.4.2 の3つの問いを、上から順に当てるだけで判定できます。

社員番号が落ちる理由が、いちばん気づきにくいところです。
社員番号は `employees` テーブルでは立派な主キーでした（1.4.2）。
**同じ列でも、どのテーブルに置かれるかで話が変わります。**

> 主キーは「その列がどういう値か」ではなく、
> **「そのテーブルの1行が、その値で1つに決まるか」**で決まる。

`employees` では「1人＝1行」なので社員番号で決まります。
予約のテーブルでは「1件の予約＝1行」なので、1人が何件も予約すれば重複します。

**選んだ答えについての補足**

複合主キーで1行に決まるなら、それを主キーにしてもよさそうに見えます。
実際、それも間違いではありません。
ただし、このテキストでは**迷ったら代理キー（連番の `id`）**という方針をとります（1.4.2）。

理由は、複合主キーにすると次の面倒が出てくるためです。

- ほかのテーブルからこの予約を指したいとき、**3列まとめて持つ**ことになる（1.2.2 の `owner_id` が3列になる）
- 予約の時間を変更したとき、**主キーの値が変わってしまう**（3条件の3つ目に反する）

**では「同じ部屋の同じ時刻に2件入る」のは、どう防ぐのか**、という疑問が残ります。
主キーとは別に、**「この3列の組み合わせは重複させない」という決まり**を列に付けられます。
これが**制約**で、第5章 5.2.3（`UNIQUE`）で扱います。

> **よくある間違い**
> 「複合主キーは難しそうだから避ける」という理由で選ばないでください。
> 第6章 6.7.1 の中間テーブルでは、**複合主キーのほうが素直な形**になります。
> 避けるのではなく、**この表では代理キーのほうが都合がよい**という選び方をしてください。

**問 2.1 の解答**

- ① **`stop`**（`down` でも可）
- ② **`-v`**
- ③ **`ready for connections`**

**解説**

①と②は、取り違えるとデータが消える組み合わせです（2.1.2）。

| コマンド | データ |
|---------|-------|
| `docker compose stop` | 残る |
| `docker compose down` | 残る（ボリュームは消えない） |
| `docker compose down -v` | **消える** |

`down` はコンテナとネットワークを消しますが、
ボリューム（`mysql-lesson_db-data`）はそのままなので、データは残ります。

MySQL は起動後に内部の準備をしています。
`docker compose logs db` の最後に `ready for connections` が出て、はじめて接続できます。

> **よくある間違い**
> ここで慌てて `docker compose down -v` からやり直す人が多い箇所です。
> **待てば解決する**ものを作り直してしまうと、原因が分からないまま時間だけが過ぎます。
> まずログを見てください。

**問 2.4 の解答**

次のうち2つが書けていれば正解です（2.2.1）。

- **文末の `;` を打ち忘れた**
- **引用符（`'`）を閉じ忘れた**
- **かっこ（`(`）を閉じ忘れた**

`shop_user` からは、**`mysql` と `sys` が見えません。**
**権限が無いものは、エラーになるのではなく、そもそも一覧に出てこない**のが特徴です。

**読み書きはできる**

```sql

```

```text

+----------+
|       20 |
+----------+
```

`shop` の中では、`root` と同じことができます。

**箱を作ることはできない**

```sql
CREATE DATABASE test1;
```

```text
ERROR 1044 (42000): Access denied for user 'shop_user'@'%' to database 'test1'
```

**パスワードを間違えたとき**

```text
ERROR 1045 (28000): Access denied for user 'shop_user'@'172.18.0.1' (using password: YES)
```

2.2.3 の表の
**「`ERROR 1045 ... Access denied ...` → パスワードが違う」**の行に当たります。

**なぜアプリからは `root` を使わないのか**

**アプリに穴があったときの被害を、そのデータベースの中だけに閉じ込めるためです**（2.2.2）。

2つの `Access denied` を見分けられることが、この演習の狙いです。

| 番号 | メッセージの形 | 意味 |
|------|--------------|------|
| **1045** | `Access denied for user 'ユーザー名'@'接続元' (using password: YES)` | **入口で断られた。** ユーザー名かパスワードが違う |

Docker のネットワーク内から繋いだので、コンテナの IP アドレスが出ています。
この数字は環境によって違います。

> **補足：`%` の意味**
> `'shop_user'@'%'` の `%` は「**どこから繋いできてもよい**」という意味です。
> MySQL のユーザーは「名前」だけでなく「**名前と接続元の組**」で管理されています。
> 同じ名前でも、接続元が違えば別のユーザーとして扱えます。
> 権限の細かい設定は、この本では扱いません。

**問 3.1 の解答**

**解説**

この3つが第3章の骨格です（3.1.1 / 3.2.1 / 3.4.1）。

| 句 | 何を決めるか |
|----|------------|
| `SELECT` | **どの列**を出すか |

| `WHERE` | **どの行**を残すか |
| `ORDER BY` | どう並べるか |
| `LIMIT` | 何件で切るか |

③については、第1章 1.3.2 の「**行に順番は無い**」が根拠です。

**問 3.2 の解答**

**2. `NULL` との比較結果は真でも偽でもなく「不明」になり、`WHERE` に残らないため**

**解説**

3.3.4 の中心にある話です。SQL の条件は**真・偽・不明**の3つの値を取り、
**`WHERE` は「真」の行だけを残します。**

```sql
SELECT 1 = NULL, NULL = NULL, NULL IS NULL;
```

```text
+----------+-------------+--------------+
| 1 = NULL | NULL = NULL | NULL IS NULL |
+----------+-------------+--------------+
|     NULL |        NULL |            1 |
+----------+-------------+--------------+
1 row in set (0.00 sec)
```

`NULL = NULL` すら真になりません。正しくは `IS NULL` を使います。

1 が誤りなのは、型のせいではないからです。`INT` の列でも `VARCHAR` の列でも同じことが起きます。
3 は SQL の話ではありません（SQL の「等しい」は `=` ひとつです。3.2.2）。
4 は事実と違います。`birthday` が `NULL` の顧客は `id` = 3 と 6 の2名います（2.5.3）。

> **この間違いが怖い理由**
> **エラーにならず、`Empty set` が返ってくる**ことです。
> 「該当者はいなかった」と読み違えたまま、次の作業に進んでしまいます。
> 0 件のときは、まず**条件そのものが成立しうるか**を疑ってください。

**問 3.4 の解答**

**2. `WHERE` は `SELECT` より先に処理されるため、別名がまだ存在しないため**

**解説**

3.4.4 の処理順の図が答えです。

```text
FROM → WHERE → SELECT → DISTINCT → ORDER BY → LIMIT
```

別名（`AS 税込価格`）が作られるのは `SELECT` の段階なので、
それより前に動く `WHERE` からは見えません。

```text
ERROR 1054 (42S22): Unknown column '税込価格' in 'where clause'
```

対処は2つあります。

```sql
-- 式をもう一度書く
SELECT name, price * 1.1 AS 税込価格 FROM products WHERE price * 1.1 >= 2000;

-- 元の列で条件を書く（こちらのほうが速い。第7章 7.5.1）
SELECT name, price * 1.1 AS 税込価格 FROM products WHERE price >= 1819;
```

1 が誤りなのは、日本語の別名自体は問題なく使えるからです（3.1.4 で実際に使いました）。
3 も誤りで、計算式にこそ別名を付けます。
4 も誤りで、`>=` は日付や文字列にも使えます（3.2.2）。

**`ORDER BY` では別名が使えます。** `ORDER BY` は `SELECT` より後に処理されるためです。

```sql
SELECT name, price * 1.1 AS 税込価格 FROM products ORDER BY 税込価格 DESC LIMIT 3;
```

```text
+----------------------------+--------------+
| name                       | 税込価格     |
+----------------------------+--------------+
| 鉄のフライパン 24cm        |       6380.0 |
| ひのきのまな板             |       4950.0 |
| 革のペンケース             |       4620.0 |
+----------------------------+--------------+
3 rows in set (0.00 sec)
```

**「`WHERE` では使えないのに `ORDER BY` では使える」**という非対称さは、
処理順の図を見れば当たり前のことになります。

**問 3.5 の解答**

**`ORDER BY` に2つ目のキー（`id` など）を足して、`ORDER BY category_id, id` にする。**

**解説**

3.4.3 の内容です。**1つ目のキーで値が並んだとき、その中の順番は決まっていません。**

```sql
SELECT id, name, category_id FROM products ORDER BY category_id;
```

分類 1 の中が `2, 3, 4, 5, 1` のような並びになるのは、
MySQL が「同じ `category_id` の行は、どう並べてもよい」と判断しているためです。

`id` は主キーなので重複しません（第1章 1.4.1）。
最後のキーに `id` を足せば、**並びは必ず1つに決まります。**

```sql
SELECT id, name, category_id FROM products ORDER BY category_id, id;
```

**この直しが効いてくるのはページ送りです。**
`LIMIT` / `OFFSET`（3.4.4）で 1ページ目と2ページ目を取るとき、
並びが確定していないと**同じ行が2回出たり、ある行が1回も出なかったり**します。

**問 3.6 の解答**

**`DISTINCT` は列ごとではなく「行（＝指定した列の組み合わせ）」の重複を見るため。
`prefecture` が同じでも `name` が違えば、別の行として両方残る。**

**解説**

3.5.1 の内容です。実際に確かめます。

```sql
SELECT DISTINCT prefecture, registered_on FROM customers;
```

```text
8 rows in set (0.00 sec)
```

東京都の顧客は3名いますが、`registered_on` がそれぞれ違うため、
**組み合わせとしては重複していません。** 結果は 8 行のままです。

「都道府県ごとに1行にして、その中の代表者も出す」というのは、
`DISTINCT` では表現できません。第6章 6.5.2 の `GROUP BY` の仕事です。

> **考え方の順番**
> `DISTINCT` を書きたくなったら、まず
> **「重複していてほしくないのは、どの列の組み合わせか」**を言葉にしてください。
> そこに出てこない列を `SELECT` に足すと、その瞬間に重複が復活します。

**問 3.7 の解答**

**`WHEN` は上から順に判定され、最初に当てはまったところで止まるため。
在庫 0 の行は先に `stock < 10` に当てはまり、`残りわずか` になってしまう。**

**解説**

3.6.4 の図のとおり、`CASE` は上から1つずつ試していきます。
`stock = 0` の行は `stock < 10` も満たすので、
**2つ目の `WHEN` まで到達しません。**

直すには、**狭い条件を先に書きます。**

```sql
CASE
    WHEN stock = 0 THEN '在庫切れ'
    WHEN stock < 10 THEN '残りわずか'
    ELSE '在庫あり'
END
```

> **見つけ方**
> このバグは、結果を眺めているだけでは気づきにくいものです。
> **`CASE` を書いたら、それぞれの分岐に当てはまる行が実際に出ているかを確かめてください。**
> 今回であれば「`在庫切れ` の行が2件あるはず」（`id` = 4 と 13）と分かっています。
> 0 件なら、条件の順番を疑います。

### 演習 3.2 の解答

```sql
SELECT DISTINCT status FROM orders ORDER BY status;
```

実行結果:

```text
+-----------------+
| status          |
+-----------------+
| キャンセル      |
| 受付            |
| 発送済          |
+-----------------+
3 rows in set (0.00 sec)
```

```sql
SELECT DISTINCT prefecture FROM customers ORDER BY prefecture;
```

実行結果:

```text
+------------+
| prefecture |
+------------+
| 京都府     |
| 北海道     |
| 大阪府     |
| 東京都     |
| 福岡県     |
+------------+
5 rows in set (0.00 sec)
```

**行数が違う理由**

`orders` は 15 行ありますが、`status` に入っている値は3種類しかありません。
`DISTINCT` は**同じ値の行を1行にまとめる**ので、3 行になります（3.5.1）。

**解説**

**知らないテーブルを渡されたときに、まず打つ SQL がこれです。**

`orders.status` が `受付` / `発送済` / `キャンセル` の3つだと、
第2章 2.5.1 の表には書いてありました。
しかし実務では、**そういう表がないまま渡されるほうが普通です。**
`DISTINCT` を1回打てば、その列が実際に取りうる値が分かります。

並び順については、**漢字とカタカナが混ざった列の「あいうえお順」は自明ではありません。**
`ORDER BY` は照合順序（2.6.3）の規則に従って並べるので、
今回は `キャンセル` が先頭に来ました。
大事なのは**順番が毎回同じになること**であって、日本語として自然な順であることではありません。
読み仮名の順に並べたい場合は、読み仮名の列を別に持つ必要があります（第5章 5.1.2 の考え方）。

> **よくある間違い**
> `SELECT status, DISTINCT ... ` のように、`DISTINCT` を途中に書くことはできません。
> **`DISTINCT` は `SELECT` の直後に1回だけ**書きます。
>
> ```text
> ERROR 1064 (42000): You have an error in your SQL syntax; ...
> ```
>
> また、`SELECT DISTINCT status, id FROM orders;` とすると **15 行**に戻ります。
> `id` は全行で違う値なので、組み合わせが重複しなくなるためです（問 3.6）。

### 演習 3.3 の解答

```sql
SELECT id, name, prefecture, registered_on
FROM customers
WHERE prefecture IN ('東京都', '大阪府')
  AND registered_on >= '2026-01-01'
ORDER BY registered_on DESC;
```

実行結果:

```text
+----+------------------+------------+---------------+
| id | name             | prefecture | registered_on |
+----+------------------+------------+---------------+
|  7 | 山本 大輔        | 大阪府     | 2026-06-01    |
|  6 | 渡辺 さくら      | 東京都     | 2026-05-16    |
|  3 | 鈴木 一郎        | 東京都     | 2026-01-25    |
+----+------------------+------------+---------------+
3 rows in set (0.00 sec)
```

**解説**

| 完成条件 | 使った内容 | 本文 |
|---------|----------|------|
| 東京都か大阪府 | `IN ('東京都', '大阪府')` | 3.3.2 |
| 列名を2回書かない | 同上（`OR` で書くと2回必要） | 3.3.2 |
| 2026年に入ってから | `registered_on >= '2026-01-01'` | 3.2.2 / 3.6.2 |
| `YEAR()` を使わない | 列をそのまま比べる形にする | 3.6.2 の「よくある間違い」 |
| 登録が新しい順 | `ORDER BY registered_on DESC` | 3.4.2 |

**`IN` を使うと、かっこの問題が起きません**

`OR` で書くこともできますが、その場合は**かっこが必須**です（3.2.4）。

```sql
-- かっこが要る書き方
SELECT id, name, prefecture, registered_on
FROM customers
WHERE (prefecture = '東京都' OR prefecture = '大阪府')
  AND registered_on >= '2026-01-01'
ORDER BY registered_on DESC;
```

かっこを外すと、`AND` が先に処理されて
「東京都の人は全員 ＋ 大阪府で 2026年以降の人」という意味になり、**4 行**になります。
`IN` を使えば、この間違いを構造的に避けられます。

**`YEAR()` を使わない理由**

```sql
-- 動くが、行が増えると遅くなる
WHERE YEAR(registered_on) = 2026
```

`WHERE` の左側に関数を置くと、MySQL は**全行に関数を掛けてから比べる**ことになります。
列をそのまま比べる形（`registered_on >= '2026-01-01'`）なら、
第7章 7.3 で扱うインデックスが使えます。

> **よくある間違い**
> `registered_on > '2026-01-01'` と `>` にすると、
> **1月1日ちょうどに登録した人が漏れます。**
> 今回のデータには該当者がいないので結果は変わりませんが、
> データが増えた日に初めて発覚する種類の間違いです。
> 「〜以降」は `>=`、「〜より後」は `>` と、日本語の側で区別してください。

### 演習 3.4 の解答

```sql
SELECT id, name, price,
    CASE
        WHEN price >= 3000 THEN '高価格帯'
        WHEN price >= 1000 THEN '中価格帯'
        ELSE '低価格帯'
```

実行結果:

```text
+----+-----------------------------------------+-------+--------------+

+----+-----------------------------------------+-------+--------------+
| 20 | 革のペンケース                          |  4200 | 高価格帯     |
| 13 | 麻のかごバスケット                      |  3600 | 高価格帯     |
| 14 | つっぱり棚                              |  2800 | 中価格帯     |
| 11 | 布のランチトート                        |  2200 | 中価格帯     |

```

**解説**

**この問題の山は `WHEN` の順番です。**

条件を「高いほうから」書く必要があります。
逆に書くと、次のようになります。

```sql
-- 間違った順番
CASE
    WHEN price >= 1000 THEN '中価格帯'
    WHEN price >= 3000 THEN '高価格帯'
    ELSE '低価格帯'
END
```

```text
+----+-----------------------------------------+-------+--------------+
| id | name                                    | price | 価格帯       |
+----+-----------------------------------------+-------+--------------+
| 20 | 革のペンケース                          |  4200 | 中価格帯     |
| 13 | 麻のかごバスケット                      |  3600 | 中価格帯     |
| 14 | つっぱり棚                              |  2800 | 中価格帯     |
...
```

**4200 円の商品まで `中価格帯` になりました。**
`price >= 1000` に先に当てはまり、そこで判定が止まるためです（3.6.4）。

「1000 円以上 3000 円未満」を `WHEN price >= 1000 AND price < 3000` と
書いてもかまいません。**その場合は順番を入れ替えても壊れません。**
条件を重ならないように書くか、順番で制御するか、どちらでも正解です。

| 完成条件 | 使った内容 | 本文 |
|---------|----------|------|
| 収納と文房具だけ | `category_id IN (3, 4)` | 3.3.2 |
| 3段階のラベル | `CASE WHEN ... THEN ...` | 3.6.4 |
| `NULL` にならない | `ELSE` を書く | 3.6.4 の「よくある間違い」 |
| 見出しが `価格帯` | `AS 価格帯` | 3.1.4 |
| 価格の高い順 | `ORDER BY price DESC` | 3.4.2 |

> **よくある間違い**
> `ELSE` を書き忘れると、1000 円未満の商品のラベルが `NULL` になります。
> エラーは出ません。
>
> ```text
> | 19 | ふせん 3色セット     |   340 | NULL         |
> ```
>
> 画面に「NULL」と表示されて初めて気づく、という順序になりがちです。
> **`CASE` を書いたら `ELSE` まで書く**のを型にしてください。

### 演習 3.5 の解答

```sql
SELECT id, name,
    CONCAT(SUBSTRING(name, 1, 2), ' 様') AS 宛名,
    DATEDIFF('2026-09-14', registered_on) AS 経過日数
FROM customers
WHERE birthday IS NOT NULL
ORDER BY registered_on ASC
LIMIT 3;
```

実行結果:

```text
+----+---------------+------------+--------------+
| id | name          | 宛名       | 経過日数     |
+----+---------------+------------+--------------+
|  1 | 田中 陽子     | 田中 様    |          315 |
|  2 | 佐藤 健       | 佐藤 様    |          270 |
|  4 | 高橋 美咲     | 高橋 様    |          217 |
+----+---------------+------------+--------------+
3 rows in set (0.00 sec)
```

**解説**

この章で扱った道具を、まとめて使う問題です。

| 完成条件 | 使った内容 | 本文 |
|---------|----------|------|
| 誕生日が登録されている人だけ | `WHERE birthday IS NOT NULL` | 3.3.4 |
| 名字を取り出す | `SUBSTRING(name, 1, 2)` | 3.6.1 |
| 「 様」を付ける | `CONCAT(..., ' 様')` | 3.6.1 |
| 経過日数 | `DATEDIFF('2026-09-14', registered_on)` | 3.6.2 |
| 見出しを付ける | `AS 宛名` / `AS 経過日数` | 3.1.4 |
| 登録が古い順 | `ORDER BY registered_on ASC` | 3.4.2 |
| 先頭の3件 | `LIMIT 3` | 3.4.4 |

**`id` = 3（鈴木 一郎）と `id` = 6（渡辺 さくら）が外れるのは、
`birthday` が `NULL` だからです**（2.5.3）。
この2名を外さないと、`ORDER BY registered_on` の3番目が変わってしまいます。

**関数は入れ子にできます**

`CONCAT(SUBSTRING(name, 1, 2), ' 様')` は、
**内側の `SUBSTRING` の戻り値が、そのまま `CONCAT` の引数になる**形です。
python-text 第5章で関数の戻り値を別の関数に渡したのと同じ構造です。

**別解**

`DATEDIFF` の代わりに `CURDATE()` を使うこともできます。

```sql
SELECT id, name,
    CONCAT(SUBSTRING(name, 1, 2), ' 様') AS 宛名,
    DATEDIFF(CURDATE(), registered_on) AS 経過日数
FROM customers
WHERE birthday IS NOT NULL
ORDER BY registered_on ASC
LIMIT 3;
```

ただし、**`CURDATE()` は実行した日によって結果が変わります。**
この演習の完成条件（`315`）で答え合わせをしたいので、日付を直接書く形を本解としました。
アプリに組み込むときは `CURDATE()` のほうが正しい、という使い分けです。

> **よくある間違い**
> `SUBSTRING(name, 0, 2)` と書くと、**空文字になります**（3.6.1）。
> Python や JavaScript の感覚で `0` から数えると、宛名が「 様」だけになります。
> エラーは出ないので、結果を見るまで気づきません。
