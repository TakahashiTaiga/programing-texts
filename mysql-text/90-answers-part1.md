## 第1章

### 理解度チェック

**問 1.1 の解答**

- ① **遅く**
- ② **消える**（あとから書き戻した人に上書きされる）
- ③ **整合性**

**解説**

3つとも 1.1 で見た問題です。

①は、1件ほしいだけでもファイルを全部読んで先頭から比べる（**全件走査**）ためです（1.1.1）。
件数が 10 倍になれば、探す手間もおよそ 10 倍になります。

②で重要なのは、**エラーが1つも出ない**ことです（1.1.2）。
2人とも「保存できた」と思っています。気づくのは、ずっとあとになってからです。

③の**整合性**は「データどうしが食い違っていない状態」のことでした（1.1.3）。
型の崩れ・表記ゆれ・項目の欠け・`id` の重複は、どれも**書いた瞬間には何も起きません。**

**問 1.2 の解答**

**2** の「テーブルは列ごとにデータ型が決まっていて、行の並び順は保証されない」

**解説**

ほかの3つが違う理由は、次のとおりです（1.3.2）。

| 選択肢 | 何が違うか |
|-------|-----------|
| 1 | **行に順番はありません。** 入れた順に返ってくる保証はない |
| 3 | テーブルのセルに**計算式は書けません。** 計算は取り出すときに書きます（第3章 3.6） |
| 4 | **同時に大勢が編集できる**ことが、データベースの得意なところです（第4章 4.5） |

選択肢 1 がとくに間違えやすいところです。
件数が少ないうちは、**たまたま入れた順に返ってくることが多い**ためです。
思い込みが表に出るのは、データが増えたときや、第7章でインデックスを張ったときです。

> **よくある間違い**
> 「じゃあ `ORDER BY` はいつ書くのか」と迷ったら、
> **画面に並べて見せるときは必ず書く**と覚えてください（第3章 3.4）。

**問 1.3 の解答**

**3** の「本人が自由に変更できるメールアドレス」

**解説**

主キーの3条件は「重複しない」「空にできない」「変わらない」でした（1.4.1）。
メールアドレスは1つ目と2つ目は満たせますが、**3つ目に反します。**

変わる値を主キーにしてはいけない理由は、**主キーが「指される側」だから**です（1.4.2）。
1.2.2 の `tasks.owner_id` を思い出してください。
もし主キーがメールアドレスだったら、`tasks` 側にもメールアドレスが入っています。
1人がアドレスを変えるたびに、**その人を指している全テーブルの全行**を直すことになります。

選択肢 4 の「生徒 `id` と授業 `id`」は、**複合主キー**として正しい形です（1.4.2 の補足）。
「主キーは1列でなければいけない」という決まりはありません。

**問 1.4 の解答**

次のうち、どれか1つが書けていれば正解です（1.2.2）。

- **表記ゆれが起きなくなる。** 担当者名は `owners` に1箇所しかなく、`tasks` には `id` しか入らないため
- **改姓しても `owners` の1行を直すだけで済む。** `tasks` 側は1行も変えなくてよい
- **存在しない担当者を指す行を拒否できる**（外部キー。第5章 5.4）
- **担当者の情報を増やすのが `owners` に列を足すだけで済む。** `tasks` は変えなくてよい

**解説**

どの答えも、根っこは同じ1点です。

> **同じ値を2箇所に持つのをやめた。**

1.1.3 の崩れは、ほとんどが「同じことを何度も書いた」ことから生まれていました。
**書く場所を1つにすれば、ずれようがありません。**

なお、**分けたら万事解決というわけではありません。**
担当者名つきの一覧を出すには、2つのテーブルを繋ぐ**結合**が必要になります（第6章）。
「どこまで分けるか」の判断基準は第5章 5.5 で扱います。

**問 1.5 の解答**

**取り出すための手順を書かず、「どういう条件のものがほしいか」だけを書くから。**
実際にどう取り出すかは DBMS が決める。

**解説**

1.2.3 で比べた2つを、もう一度並べます。

```python
result = []
for task in tasks:
    if not task["done"]:
        result.append(task["title"])
result.sort()
```

```sql
SELECT title FROM tasks WHERE done = 0 ORDER BY title;
```

Python のほうは、**行の順番を入れ替えると結果が変わります。**
「1件ずつ見る」「条件に合えば足す」「最後に並べ替える」という手順そのものだからです。

SQL のほうには、手順が1つも書かれていません。
「未完了の」「タイトルを」「順に並べて」という**条件だけ**です。

これは手抜きではなく、利点です。
データが 10 万件に増えたとき、**SQL を1文字も変えずに、
DBMS 側が効率のよい取り出し方に切り替えられます。**
DBMS が選んだ取り出し方を確認する方法は、第7章 7.4（実行計画）で扱います。

**問 1.6 の解答**

**`NULL` は「値がそもそも入っていない」状態、空文字（`''`）は「空という値が入っている」状態。**

**解説**

住所欄で考えると分かりやすくなります（1.3.1）。

| 状態 | 意味 |
|------|------|
| `NULL` | **まだ聞いていない。** 住所があるのかどうかも分からない |
| `''`（空文字） | **聞いたうえで、空だった。** 長さ 0 の文字列が入っている |

この違いは、第3章 3.3.4 で検索条件を書くときに効いてきます。
`NULL` は「等しいか」で比べられないため、専用の書き方（`IS NULL`）を使います。

> **補足**
> Python の `None`、JavaScript の `null` に近いものですが、
> **比べ方が違う**点だけ、いまのうちに引っかかりとして覚えておいてください。

**問 1.7 の解答**

**MySQL はサーバー型で、専用のプログラムを起動してそこへ接続する。
SQLite はファイル型で、専用のプログラムを起動せず1つのファイルを直接読み書きする。**

**解説**

fastapi-text 第6章で「データベースサーバーを起動する」作業をしなかったのは、
SQLite がファイル型だったからです（1.5.1）。
保存先は `app.db` という**1つのファイル**だけでした。

この本で MySQL を使うには、第2章で**先に MySQL を起動しておく**必要があります。
第0章 0.1.1 で Docker が使えるかを確認したのは、この起動のためです。

形が違うと、得意なことも変わります。

| | MySQL（サーバー型） | SQLite（ファイル型） |
|---|-----------------|------------------|
| 大勢が同時に書く | 得意 | 苦手（書き込みは1つずつ） |
| 準備 | 起動が必要 | 不要 |
| 向いている場面 | Web アプリの本番 | 手元の試作、アプリへの同梱 |

**書く SQL は、ほとんど同じです。** 違うのは準備と運用の部分です。

### 演習問題

### 演習 1.1 の解答

**テーブルの設計（解答例）**

**items**

| 列名 | 入れるデータの種類 | 補足 |
|------|-----------------|------|
| `id` | 整数 | **主キー** |
| `name` | 文字列 | 商品名 |
| `price` | 整数 | 円単位。1.3.1 の `INT` にあたる |
| `stock` | 整数 | 在庫数 |
| `category` | 文字列 | 分類 |

**主キー：`id`**

理由：**行を1つに特定するために用意された、意味を持たない連番だから**（1.4.2 の代理キー）。
`name` は同じ商品名が入る可能性があり、`category` は明らかに重複します。

**JSON に入っていた4つの崩れ**

| 崩れ | どこ | テーブルではなぜ起きないか |
|------|------|------------------------|
| 型がそろっていない | `"price": "800"` が文字列 | `price` 列を整数型にすると、**文字列は入らない**（1.3.1） |
| 表記がゆれている | `"category": "食器 "` に余分な空白 | **これはテーブルにしても防げません**（下記） |
| 項目が欠けている | `id: 3` の1行目に `stock` が無い | テーブルは**すべての行が同じ列を持つ**ので、列が消えることはない（1.2.1） |
| `id` が重複している | `id: 3` が2行ある | `id` を**主キー**にすると、同じ値は2行目で拒否される（1.4.1） |

**`stock` が `null` の行と `0` の行の違い**

- `0`：**在庫数を数えた結果、0 個だった**
- `null`（`NULL`）：**在庫数がまだ分からない。** 数えていない、あるいは記録していない

「在庫切れの商品を一覧する」ときに、この2つを同じに扱うと結果が変わります（1.3.1、第3章 3.3.4）。

**テーブルの形にしても、まだ防げないもの**

**`"食器"` と `"食器 "` の表記ゆれです。**

どちらも文字列としては正しい値なので、型の検査でも「空にしない」制約でも止まりません（1.1.3）。
このままだと、「食器の商品を数える」ときに2つに割れて出てきます。

根本的に直すには、**分類を別のテーブルに分けて、`items` は分類の `id` を持つ**形にします（1.2.2）。
そうすれば、「食器」という文字列は `categories` テーブルに1箇所しか存在しなくなります。

**解説**

この演習の狙いは、**「テーブルにすれば全部きれいになる」わけではない**と気づくことです。

テーブルの形が自動で防いでくれるのは、次の3つです。

1. **型の崩れ**（列の型で止まる）
2. **項目の欠け**（列が固定されているので起きない）
3. **主キーの重複**（主キーの制約で止まる）

一方で、**「同じ意味の値が、違う文字列で入る」問題は残ります。**
これを止めるのが 1.2.2 の「表を分ける」という考え方で、演習 1.2 でそれを実際にやります。

> **別解**
> `price` を整数ではなく小数の型にした人もいるかもしれません。
> 金額に小数の型を使うと、計算がわずかにずれることがあります。
> **金額を浮動小数点数で持たない**理由は、第5章 5.1.5 で扱います。
> この演習では、円単位の整数にしておけば十分です。

### 演習 1.2 の解答

**分けたあとのテーブル（解答例）**

**authors**（著者）

| id | name | birth_year |
|----|------|-----------|
| 1 | 夏目漱石 | 1867 |
| 2 | 芥川龍之介 | 1892 |

**books**（書籍）

| id | title | author_id |
|----|-------|-----------|
| 1 | 吾輩は猫である | 1 |
| 2 | こころ | 1 |
| 3 | 坊っちゃん | 1 |
| 4 | 羅生門 | 2 |

**members**（利用者）

| id | name |
|----|------|
| 1 | 田中 |
| 2 | 佐藤 |

**loans**（貸出）

| id | book_id | member_id | loaned_on |
|----|---------|-----------|-----------|
| 1 | 1 | 1 | 2026-09-01 |
| 2 | 2 | 2 | 2026-09-02 |
| 3 | 3 | 1 | 2026-09-03 |
| 4 | 4 | 1 | 2026-09-05 |

**主キー**：4つとも `id` 列（代理キー。1.4.2）

**相手の主キーを持つ列**（1.2.2 の手順4にあたるもの）

| どのテーブルの、どの列 | 何を指しているか |
|--------------------|----------------|
| `books.author_id` | `authors.id` |
| `loans.book_id` | `books.id` |
| `loans.member_id` | `members.id` |

3つあります。**1つのテーブルが2つ持つことも問題ありません**（`loans`）。

**もとの表にあった崩れと、解決したこと**

崩れ：**3行目の著者名が「夏目 漱石」になっている**（ほかの行は「夏目漱石」）。

分けたあと、著者名は `authors` テーブルに**1行しか存在しません。**
`books` が持っているのは `author_id` という数値だけなので、
**そもそも著者名を書き間違える場所がなくなりました。**

**増える手間**

「誰が、いつ、何という本を、誰の著書で借りたか」を1枚の表として見たいときは、
`loans` / `books` / `authors` / `members` の**4つを繋ぐ**必要があります。
この操作が**結合（JOIN）**で、**第6章**で扱います（3つ以上の結合は 6.4）。

**解説**

1.2.2 の4つの手順を、繰り返し出てくる列の数だけ回すのがこの演習です。

| 回 | 1. 繰り返している列 | 2〜3. 作る表 | 4. もとの表が持つ列 |
|----|------------------|------------|------------------|
| 1周目 | `book_author` / `author_birth_year` | `authors` | `books.author_id` |
| 2周目 | `member_name` | `members` | `loans.member_id` |
| 3周目 | `book_title` | `books` | `loans.book_id` |

**`author_birth_year` を `authors` に置く理由**が、この演習のいちばんの山です。

生年は**著者に属する情報**であって、本にも貸出にも属していません。
`books` に置くと、夏目漱石の本が3冊あるだけで `1867` が3回書かれます。
**生年が間違っていたときに3箇所直す**ことになり、1.1.3 の状態に逆戻りです。

判断の基準は 1.2.2 の手順2、
**「その値と、それにくっついてくる情報をまとめて別の表にする」**です。
「この値は、何が決まれば決まるのか」を考えてください。
生年は**著者が決まれば決まります。** だから `authors` に置きます。

> **別解**
> `books` を作らず、`loans` に `book_title` と `author_id` を直接持たせた人もいるかもしれません。
> 同じ本が2回貸し出されたときに書名が2回書かれるので、表記ゆれの余地が残ります。
> ただし、**「この図書館は同じ本を2回貸さない」という前提があるなら、それでも成り立ちます。**
> テーブルの分け方は、**扱う対象のルールによって変わります。**
> どこまで分けるかの判断基準は、第5章 5.5 で扱います。

> **よくある間違い**
> `loans` に主キーを付け忘れる人が多い箇所です。
> 「同じ人が同じ本を、別の日にもう一度借りる」ことがあるので、
> `book_id` と `member_id` の組だけでは1行に決まりません（1.4.1）。
> 連番の `id` を用意するか、`loaned_on` まで含めた組にする必要があります。

### 演習 1.3 の解答

**主キーの候補の評価（解答例）**

| 候補 | 重複しないか | 空にならないか | 変わらないか | 判定 |
|------|------------|--------------|------------|------|
| 会議室の名前 | ✕ 同じ部屋を何度も予約する | ○ | △ 部屋名を変えることはある | **✕** |
| 予約した人の社員番号 | ✕ 1人が何件も予約する | ○ | ○ | **✕** |
| 予約した日付 | ✕ 同じ日に何件も予約が入る | ○ | ✕ 予約日を変更することがある | **✕** |
| 予約の目的 | ✕ 「定例会議」が何度も入る | ✕ 空欄のことがある | ✕ あとから書き換えられる | **✕** |
| 連番の `id` | ○ | ○ | ○ | **○** |

**選んだ主キー：連番の `id`**

理由：**3つの条件をすべて満たし、現実の都合で値が変わることがないから**（1.4.2 の代理キー）。

**「予約の目的」を主キーにしてはいけない理由**

3条件の**すべてに反します。** とくに決定的なのは2つ目で、
**空欄のことがある**ためです。主キーは空（`NULL`）にできません（1.4.1）。

**「会議室の名前」だけでは主キーにできない理由**

**同じ会議室が何度も予約されるので、値が重複します**（1.4.1 の1つ目の条件）。
「第1会議室」という値の行が、何十行も並ぶことになります。

**複数の列を組み合わせれば決まる組み合わせ**

**「会議室の名前 ＋ 予約した日付 ＋ 開始時刻」**の3列の組み合わせです。
同じ部屋の、同じ日の、同じ時刻に2件の予約は入らないので、これで1行に決まります。

この形を**複合主キー**と呼びます（1.4.2 の補足）。

**解説**

この演習で確かめてほしいのは、
**「1列ずつ順に見ていけば、候補は機械的に落とせる」**ということです。
1.4.2 の3つの問いを、上から順に当てるだけで判定できます。

社員番号が落ちる理由が、いちばん気づきにくいところです。
社員番号は `employees` テーブルでは立派な主キーでした（1.4.2）。
**同じ列でも、どのテーブルに置かれるかで話が変わります。**

> 主キーは「その列がどういう値か」ではなく、
> **「そのテーブルの1行が、その値で1つに決まるか」**で決まる。

`employees` では「1人＝1行」なので社員番号で決まります。
予約のテーブルでは「1件の予約＝1行」なので、1人が何件も予約すれば重複します。

**選んだ答えについての補足**

複合主キーで1行に決まるなら、それを主キーにしてもよさそうに見えます。
実際、それも間違いではありません。
ただし、このテキストでは**迷ったら代理キー（連番の `id`）**という方針をとります（1.4.2）。

理由は、複合主キーにすると次の面倒が出てくるためです。

- ほかのテーブルからこの予約を指したいとき、**3列まとめて持つ**ことになる（1.2.2 の `owner_id` が3列になる）
- 予約の時間を変更したとき、**主キーの値が変わってしまう**（3条件の3つ目に反する）

**では「同じ部屋の同じ時刻に2件入る」のは、どう防ぐのか**、という疑問が残ります。
主キーとは別に、**「この3列の組み合わせは重複させない」という決まり**を列に付けられます。
これが**制約**で、第5章 5.2.3（`UNIQUE`）で扱います。

> **よくある間違い**
> 「複合主キーは難しそうだから避ける」という理由で選ばないでください。
> 第6章 6.7.1 の中間テーブルでは、**複合主キーのほうが素直な形**になります。
> 避けるのではなく、**この表では代理キーのほうが都合がよい**という選び方をしてください。
