# 執筆タスク実行手順書（RUNBOOK）

このリポジトリの執筆を、**1回の実行で1タスクずつ**進めるための手順書です。
Claude のクラウドルーティン（定期実行エージェント）に、
下記のプロンプトをそのまま設定して回します。

- タスクの一覧と進捗：[`TASKS.md`](./TASKS.md)
- 章立て（何を書くか）：各テキストの `README.md`

---

## 1. この仕組みの考え方

```
docs/writing-tasks/TASKS.md   ← 全59タスクのキュー（状態付き）
        │
        │  ルーティンが毎回ここを読んで、
        │  「進行中」または最初の「未着手」を1件取る
        ↓
    ブランチを切る（task/<ID>-<slug>）
        ↓
    1タスク = 1章の執筆
        ├ 本文を書く          （<book>/NN-slug.md）
        │   ├ 演習に必要な知識は本文で説明しきる（3.6）
        │   └ 表で表現しきれない図は Mermaid / SVG→PNG（3.7）
        ├ 解答編に追記する    （<book>/90-answers-*.md）
        ├ curriculum-map 更新 （ai/curriculum-map.md）
        └ TASKS.md の状態を更新
        ↓
    コミット → プッシュ → プルリクエスト作成（マージはしない）
```

**1回の実行で複数タスクを進めないでください。**
1タスク1PRにすることで、内容が気に入らなければそのPRだけ却下・修正できます。
**main には直接コミットしません。** 必ずブランチを切ってPRを作成してください。

## 2. ルーティンに設定するプロンプト

**以下をそのままコピーして、ルーティンのプロンプト欄に貼り付けてください。**
毎回同じ内容で構いません。タスクの選択は Claude が `TASKS.md` を見て判断します。

```text
このリポジトリは、プログラミング未経験者向けの学習テキスト集です。
執筆タスクを1件だけ実行してください。

## 手順

1. 次のファイルを読んで、執筆ルールを把握する
   - CLAUDE.md
   - docs/writing-guidelines.md   ← 6章「図解」、3.6「演習と本文の整合性」を含む
   - docs/style-guide.md
   - docs/glossary.md
   - docs/writing-tasks/RUNBOOK.md   ← 完成条件とPRの出し方はここに全部書いてある

2. git checkout main && git pull origin main で最新化する

3. **対象タスクを選ぶ前に、GitHub 上の open な PR を確認する**（**4.6 参照。省略しない**）
   - open な PR のブランチ名 task/<ID>-* から、対応するタスク ID を洗い出す
   - **TASKS.md 上は「未着手」でも、対応する open な PR がすでにあるタスクは選ばない**
     （main の TASKS.md が更新される前に複数回実行されると、同じタスクを重複して
     書いてしまうことがある。これを防ぐための確認）
   - 該当タスクを見つけたら、4.6 の手順に従って TASKS.md を補正してから、
     補正後の状態で次のステップに進む

4. docs/writing-tasks/TASKS.md を読み、対象タスクを1件だけ選ぶ
   - 状態が「進行中」のタスクがあれば、対応する既存ブランチ task/<ID>-* を
     checkout して続きを書く（新しいブランチや新しいPRは作らない）
   - なければ、上から見て最初の「未着手」のタスク（ただし手順3で
     「open な PR がある」と確認したものは除く）を選び、
     git checkout -b task/<ID>-<短い英語スラッグ> で新しいブランチを作る
     例: task/R-04-js-basics

5. 対象の本の README.md を読み、そのタスクが担当する章の
   節（X.Y）・項（X.Y.Z）をすべて確認する

6. 同じ本の直前の章（すでに執筆済みのもの）を1つ読み、
   文体・構成・分量・囲み記事の使い方を揃える
   ※ その本にまだ執筆済みの章がない場合は react-text/02-html.md を参照する

7. 本文を執筆する（RUNBOOK の「3. 共通の完成条件」を必ず満たすこと）
   - 演習問題を書いたら、3.6 の自己点検を必ず行う
     （演習の完成条件を満たす知識が本文のどの項にあるか、番号を挙げられるか）
     指させない箇所があれば、演習を易しくせず本文を加筆する
   - 表で表現しきれない図は 3.7 に従って Mermaid か SVG→PNG で作る

8. 演習問題の解答と解説を、同じ本の解答編ファイルに追記する

9. ai/curriculum-map.md の該当行を、実際に書いた内容に合わせて更新する

10. docs/writing-tasks/TASKS.md の、そのタスクの状態を「完了」に更新する

11. 変更をコミットし、ブランチをプッシュしてプルリクエストを作成する
    （RUNBOOK の「4. コミット・PRの出し方」に従う）

## 重要な制約

- 1回の実行で扱うタスクは **1件だけ**。終わったら次のタスクに進まず終了すること
- **タスクを選ぶ前に、必ず open な PR を確認する**（4.6）。確認せずに着手しない
- **main に直接コミットしない。** 必ずブランチを切り、最後は PR を作成する
- **作成した PR はマージしない。** 人間のレビュー待ちとして残す
- 対象読者は **プログラミング未経験者**。既知として扱ってよいのは PC の基本操作まで
- 章番号は X.Y.Z の3階層。README.md の章立てにある項を勝手に削らない
- **演習問題を易しくすることで帳尻を合わせない。** 足りないのは本文の説明
- 図に逃げられるものを、無理に文章や表だけで説明しない
- **解答編への追記を忘れない**（これが最も抜けやすい工程）
- 学習者がその章より先の内容を使わない（ai/curriculum-map.md を参照）
- コードはすべて実行可能にする
- 環境依存の手順は Windows / macOS の両方を書く
- 日本語・ですます調

最後に、どの章のどの範囲を書いたか、作成した PR の URL を1〜3行で報告してください。
```

## 3. すべてのタスク共通の完成条件

執筆タスク（`-FIN` を除く全タスク）は、次をすべて満たしたら完了です。

### 3.1 本文の構成

- [ ] frontmatter（`---` で囲んだ `title:`）がファイル先頭にある
- [ ] 章タイトルの `# 見出し` がある
- [ ] 「この章で学ぶこと」（箇条書き3〜6個、「〜できるようになる」の形）
- [ ] 「この章の前提」
- [ ] 冒頭に「つまずいたら」の囲み記事
- [ ] README.md の章立てにある**すべての節・項**が、番号付きで存在する
- [ ] 「まとめ」（箇条書き5〜12個）
- [ ] 「理解度チェック」（3〜7問）
- [ ] 「演習問題」（2〜5問、★の難易度付き）
- [ ] 「次の章へ」と次章へのリンク

### 3.2 書き方

- [ ] すべての項に `N.M.L` の番号が振られている（`####` 以下は使わない）
- [ ] 初出の専門用語すべてに、その場で1行の説明がある
- [ ] コードブロックすべてに言語指定がある
- [ ] コードを書く**ファイル名と場所**が明示されている
- [ ] コードの**実行結果**が示されている
- [ ] 環境依存の手順が Windows / macOS 両方ある
- [ ] 「よくある間違い」の囲み記事が、詰まりやすい箇所に置かれている
- [ ] 「簡単です」「すぐできます」を使っていない

### 3.3 演習問題と本文の整合性（重要）

- [ ] 各問に「課題」「完成条件」「ヒント」の3つがある
- [ ] 完成条件が、学習者自身でチェックできる形になっている
- [ ] ヒントは方向を示すだけで、答えを書いていない
- [ ] ★☆☆ が最低1問ある（本文を少し変えればできるもの）
- [ ] **演習の完成条件を1つずつ確認し、それを満たす知識が本文のどの項にあるか
      番号を挙げられる。** 挙げられない場合は演習を削らず、本文にその説明を足した
- [ ] ★★☆ 以上の演習には、要素の組み合わせ方そのものを示す例が本文にある
      （要素ごとの説明だけで終わっていない）

> 演習が難しく感じるのは、たいてい演習の難易度ではなく本文の説明不足が原因。
> 詳細は `docs/writing-guidelines.md` の 3.6 を参照。

### 3.4 解答編（**最重要・最も抜けやすい**）

- [ ] 理解度チェックの全問に解答がある
- [ ] 演習問題の全問に解答がある
- [ ] **すべての解答に「解説」が付いている**（コードだけ置かない）
- [ ] 見出しが本文の番号と完全に対応している（`### 演習 5.2 の解答`）
- [ ] 「よくある間違い」や別解が添えられている

### 3.5 リンクと整合性

- [ ] 相対リンクがすべて実在するファイルを指している
- [ ] 前章・次章へのリンクが正しい
- [ ] `ai/curriculum-map.md` の既習範囲が、実際に書いた内容と一致している
- [ ] 対象の本の `config.yaml` の `chapters` にファイル名が含まれている

### 3.6 演習に必要な知識は本文で説明しきる（自己点検の手順）

1. 演習問題を書き終えたら、各問の完成条件を1項目ずつ見る
2. 「これを満たすための知識・構文・考え方は、本文のどの `X.Y.Z` で説明したか」を答える
3. 答えられない項目があれば、**演習ではなく本文を直す**
   - 演習とは違う題材の具体例を、その概念の説明のすぐあとに1つ加える
   - 演習文中に出てくる語彙が本文で拾えているか確認する
   - 「よくある間違い」を、演習で踏みやすい落とし穴に絞って追加する
4. もう一度 1 に戻って確認する

判断基準：**本文を読んだだけで、`ai/hint-policy.md` のヒント1段階目だけで
手が動き出せるか。** 動き出せないなら本文の説明不足。

### 3.7 図解（Mermaid / SVG）

表で表現しきれない流れ・構造・位置関係は図にする。詳細は
`docs/writing-guidelines.md` の「6. 図解」を参照。要点だけ:

- **まず Mermaid を検討する。** Zenn・GitHub 両方でそのまま描画され、画像ファイル管理が不要
  （フローチャート、シーケンス図、ER図、状態遷移、Git ブランチなど）
- Mermaid で表現できない図（ボックスモデル、Flexbox の軸など）は SVG で作図し、
  **PNG に変換してから**本文で参照する
  - 原本：`<book>/images/svg-src/NN-slug.svg`
  - 埋め込み用：`<book>/images/NN-slug.png`
- **`.svg` を本文から直接 `![]()` で参照しない。** Zenn が `.svg` を画像として認識しないため
- その場で PNG 変換ができない環境の場合は、SVG ソースだけ保存し、
  本文に `<!-- TODO(review-notes): ... -->` のプレースホルダを残し、
  `docs/writing-tasks/review-notes.md` の「図解の変換待ち」に追記して人間に引き継ぐ

## 4. コミット・PRの出し方

### 4.1 ブランチ名

```
task/<タスクID>-<短い英語スラッグ>
```

例：`task/R-04-js-basics`、`task/M-06-join-and-aggregate`

### 4.2 コミット

```bash
git add <変更したファイル>
git commit -m "R-04: react-text 第4章 JavaScript の基礎（前半）を執筆"
```

### 4.3 プッシュと PR 作成

```bash
git push -u origin task/R-04-js-basics

gh pr create \
  --base main \
  --title "R-04: react-text 第4章 JavaScript の基礎（前半）" \
  --body "$(cat <<'EOF'
## 対象タスク
R-04（docs/writing-tasks/TASKS.md）

## 書いた範囲
react-text/04-javascript-basics.md（4.1〜4.6 すべて）

## 解答編
90-answers-part1.md の「第4章」に追記した

## 演習と本文の整合性チェック（3.6）
各演習の完成条件に対応する本文の項番号を確認済み

## 図解
なし / Mermaid で ○○ の図を追加 / SVG→PNG で ○○ の図を追加

## 要検証・申し送り
docs/writing-tasks/review-notes.md への追記: なし / あり（内容）
EOF
)"
```

### 4.4 進行中タスクの再開

前回「進行中」で終わったタスクを続ける場合は、**新しいブランチを作らない。**

```bash
git checkout task/R-04-js-basics
git pull origin task/R-04-js-basics
# 続きを執筆
git add <変更したファイル>
git commit -m "R-04: 4.5〜4.6 を追記して完了"
git push
```

既存の PR に自動的に追加コミットとして反映される（`gh pr create` は不要）。

### 4.5 PR はマージしない

**ルーティンは PR を作成するところまで。マージは人間が行います。**
レビューし、必要なら修正を指示してから、人間が GitHub 上でマージしてください。

### 4.6 着手前に open な PR を確認する（重複執筆の防止）

**背景**：`main` の `TASKS.md` は、PR がマージされて初めて更新されます。
PR が未マージのまま次の実行が走ると、`main` 側は「未着手」に見えたままなので、
**同じタスクを2回書いてしまいます。** これを防ぐため、タスクを選ぶ前に必ず確認します。

**手順**

1. open な PR の一覧を取得する（`gh` が使える場合）

   ```bash
   gh pr list --state open --json number,title,headRefName,url
   ```

   `gh` が使えない環境では、GitHub の PR 一覧 API・MCP ツールなど、
   使える手段で同じ情報（open な PR のブランチ名一覧）を取得してください。

2. 各 PR の `headRefName`（ブランチ名）から `task/<ID>-*` の `<ID>` を読み取る

3. TASKS.md の状態と突き合わせる

   | 状況 | 対応 |
   |------|------|
   | 対応する PR がなく、TASKS.md も「未着手」 | 通常どおりそのタスクに着手してよい |
   | 対応する PR があり、TASKS.md が「未着手」のまま | **重複の兆候。次の a〜c で処理する** |
   | 対応する PR があり、TASKS.md もすでに「完了」 | マージ待ちの通常状態。そのタスクは選ばない |

   **a〜c（PR があるのに TASKS.md が未着手のときの処理）**

   a. その PR のブランチ（例：`task/R-04-js-basics`）の内容を確認する
      （`git fetch origin <branch> && git show origin/<branch>:docs/writing-tasks/TASKS.md` など）

   b. 本文・解答編・curriculum-map の更新まで完了しているように見えれば、
      **そのタスクは実質「完了」として扱う。** 自分のローカルの `TASKS.md`
      （まだ push しない作業コピー）で該当行を「完了」に補正してから、
      手順4で**次の**「未着手」タスクを選ぶ
      - この補正は、選んだ次のタスクの PR に含めてコミットしてよい
        （「TASKS.md の反映漏れを補正」の1行を添える）
      - 別タスクの内容を厚く直すようなことはしない。状態の反映漏れの補正のみ

   c. 逆に、その PR の内容が明らかに未完成（`🚧 執筆中です` のプレースホルダのまま、
      演習や解答編が抜けているなど）であれば、**新しいブランチは作らず**、
      既存のブランチ（例：`task/R-04-js-basics`）を checkout して**続きを書く**
      （4.4 と同じ扱い。新しい PR は作らない）

4. 上記で「選ばない」と判定したタスクは、通常の選定（4章の手順4）から除外する

> **なぜ「次のタスクに進んでよい」のか**
> RUNBOOK 冒頭の「1回の実行で複数タスクを進めない」という制約は、
> **1つのタスクを最初から最後まで書き切る**ことを指しています。
> すでに他の実行で完了しているタスクを検出して次に進むのは、
> 新しいタスクに1回だけ着手することと同じであり、この制約に反しません。

## 5. 分量の目安

| 規模 | 目安 | 1回の実行で |
|------|------|-----------|
| 小 | 3,000〜6,000字 | 余裕を持って完了する |
| 中 | 6,000〜12,000字 | 1回で完了する |
| 大 | 12,000〜20,000字 | 1回で終わらない可能性がある |

### 1回の実行で終わらなかった場合

**無理に短くまとめないでください。** 途中で切り上げて、次回に続けます。

1. そこまでの内容を保存する
2. `TASKS.md` の状態を **「進行中」** にし、備考欄に到達点を書く
   例：`進行中（4.4 まで完了。次は 4.5 繰り返しから）`
3. 同じブランチにコミットしてプッシュする（4.4 参照）。PR が未作成なら作成する

次回の実行では、「進行中」のタスクが優先的に選ばれ、同じブランチで続きから再開されます。

## 6. 人間がやること（ルーティンには任せない）

| 作業 | タイミング |
|------|-----------|
| **PR をレビューしてマージする** | PR が作成されるたび |
| 書かれた章を読んで、内容の妥当性を確認する | PR レビュー時 |
| SVG ソースから PNG への変換（自動化できなかった分） | `review-notes.md` の「図解の変換待ち」を見て随時 |
| 用語のブレ・説明の重複を直す | 1冊終わったとき（`-FIN` タスク） |
| スクリーンショット画像の撮影と配置 | 1冊終わったとき |
| Zenn への公開設定（`published: true`） | 1冊完成後 |
| 実際にコードを動かして検証する | 気になった章 |

> **AI が書いた技術文章は、コマンドやバージョンが実在しないことがあります。**
> 環境構築の章（各本の第1〜2章）だけは、**必ず自分で通しで実行して確認**してください。

> **PR が未マージのまま積み上がると、後続タスクが古い main を基準に作業してしまいます。**
> なるべくこまめにレビュー・マージしてください。

## 7. ルーティンの設定方法

Claude Code のクラウドルーティン（スケジュール実行）で設定します。

- **プロンプト**：上記「2. ルーティンに設定するプロンプト」の内容
- **リポジトリ**：`TakahashiTaiga/programing-texts`
- **ベースブランチ**：`main`（作業は毎回ここから新しいブランチを切る）
- **頻度**：1日1〜2回程度を推奨
- **前提**：実行環境で `gh`（GitHub CLI）がこのリポジトリに対して認証済みであること
  （4.6 の「着手前に open な PR を確認する」に使う。`gh` の代わりに GitHub の
  MCP ツールなど、open な PR の一覧を取得できる別の手段でも構わない）

> **頻度を上げすぎないでください。**
> 内容を人間が読んで確認する時間が取れなくなり、
> レビュー待ちの PR ばかりが積み上がっていくことになります。

### 途中で止めたいとき

`TASKS.md` の先頭に次の1行を書き加えると、ルーティンは何もせずに終了します。

```
<!-- PAUSE: 執筆を一時停止中 -->
```

## 8. トラブルシューティング

| 症状 | 対処 |
